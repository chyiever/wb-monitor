# 2026-07-18 Tab3 FIP 丢帧缺口与首点 0 分析修复

## 1. 日志范围

- 分析日志：`logs/pccp_monitor.log`
- 本轮重点时间段：2026-07-18 00:26:42 至 2026-07-18 00:40:21
- 运行参数：日志显示 Tab1 FIP 配置为 `sensor_count=2 selected=FIP1 duration=1.000000s sample_rate=1000000.0Hz`。

## 2. 结论摘要

1. Tab3 当前看到的缺口不是 DAS TCP 通信丢包导致。日志中 DAS 统计持续显示 `missing=0`，`DASPlotWorker` 统计显示 `dropped=0`，说明 DAS 接收和 DAS 绘图队列没有丢帧证据。
2. FIP 缺口来自 Tab1 的 `DataProcessingThread` 处理队列满后丢弃旧 FIP 包。日志明确出现 `Processing queue full, discarded old packet #177 to admit packet #277`，随后出现 `comm_count gap in DataProcessingThread: last=176, current=180, missing=3`。
3. 现有日志不能直接证明“Tab3 FIP 未滤波波形第一个点为 0”是原始数据本身为 0。旧日志没有记录 TCP 原始首样本、处理链首样本和 UI 最终绘制首样本。
4. 从代码路径看，原 Tab3 FIP 曲线使用的是 `processed_data.downsampled_data`，即“相位展开 -> 滤波 -> 降采样”后的数据，不是未滤波数据。因此首点 0 可能来自原始首样本、滤波初始态、或缺口后的状态重置影响，但旧日志不足以一锤定音。
5. `PhaseUnwrapper.reset()` 不会主动把每包第一个点置 0；它只清除上一包相位连续性状态。若新包输入首样本不为 0，相位展开结果的首点也不应因为 reset 被强制变成 0。
6. 日志中 FIP 解析后的范围长期为 `[-2147483648, 2147483648]`，远超 `PhaseUnwrapper` 期望的 `[-1, 1]` 包裹相位范围。该问题不能通过软件猜测性缩放掩盖，后续必须由新增日志确认发送端真实 `<32,32>` 原始 int64 范围和协议含义。

## 3. 逐项问题梳理

### P1 FIP 处理队列满导致 Tab3 FIP 缺口

日志证据：

- 2026-07-18 00:32:24 起，`DataProcessingThread` 连续出现 `Processing queue full, discarded old packet`。
- 紧随其后出现多条 `comm_count gap in DataProcessingThread`，例如 `last=176, current=180, missing=3`、`last=180, current=183, missing=2`。

原因：

- 双 FIP、1 MHz、1 s 包时，每包总计 2,000,000 点。
- 原处理链对 FIP1/FIP2 都执行相位展开、滤波和降采样，CPU 负载偏高。
- Tab3 FIP 又依赖 Tab1 处理线程输出，因此处理线程丢旧包会直接表现为 Tab3 FIP 缺口。

修复：

- `DataProcessingThread` 保留两路 FIP 的相位展开和未滤波降采样。
- 只有 Tab1 当前选中的 `绘图FIP` 继续执行滤波和滤波后降采样，非选中 FIP 跳过滤波路径，减少双 FIP 每包 CPU 负载。
- 新增 `FIP_PROCESS_STATS` 日志，记录处理包数、入队数、当前队列深度、峰值、丢弃数、缺口数、平均处理耗时和最大处理耗时。

### P2 Tab3 FIP 曲线实际使用了滤波数据

旧代码路径：

```text
DataProcessingThread._process_packet()
  -> signal_filter.apply_filter(unwrapped)
  -> downsampler.downsample(filtered)
  -> ProcessedData.downsampled_data
  -> DASTab3Manager.process_fip_processed_data()
  -> MainWindow.update_tab3_fip_curve()
```

问题：

- 用户观察的是“未滤波 FIP 波形”，但旧 Tab3 实际绘制 `downsampled_data`，是滤波后数据。
- 若滤波器状态在缺口后重置，滤波器初始态可能引入首点瞬态，导致首点是否为原始数据无法判断。

修复：

- Tab3 FIP 曲线和 joint 存储改用 `ProcessedData.psd_data` / `psd_by_sensor`，即相位展开后、未滤波、按当前降采样因子抽取的数据。
- `FIPSessionPacket.unwrapped_data`、`display_data`、`unwrapped_by_sensor`、`display_by_sensor` 在 Tab3 中统一保存未滤波降采样数据。

### P3 joint 存储中 FIP 采样率与数组长度不一致

旧问题：

- `FIPSessionPacket.sample_rate_hz` 使用 `processed_data.effective_rate`，默认约 200 kHz。
- 但 `unwrapped_data` 旧代码传入的是 1 MHz 全量 `processed_data.unwrapped_data`。
- 这会导致 joint `.npz` 的 `fip_raw_200khz` 字段名、`fip_sample_rate_hz` 和实际数组长度语义不一致。

修复：

- Tab3 joint 存储写入的 FIP 数组改为未滤波降采样数据，长度与 `fip_sample_rate_hz` 匹配。
- `fip1_raw_200khz`、`fip2_raw_200khz`、`fip_raw_200khz` 仍保留历史字段名，但实际采样率以 `fip_sample_rate_hz` 为准。

### P4 旧处理链存在猜测性幅值缩放

旧代码：

```python
if np.max(np.abs(phase_data)) > 5:
    phase_data = phase_data / np.pi
```

问题：

- 该逻辑会在没有明确数据来源语义的情况下改变幅值。
- 用户明确要求保持数据真实性和完整性，因此不能通过自动缩放掩盖发送端或协议问题。

修复：

- 删除处理链和存储链中的 `> 5` 自动除以 `pi` 逻辑。
- 新增 `validate_wrapped_phase_input()` 只做范围诊断，不做幅值缩放、不修复非有限值。
- TCP `<32,32>` 的 `int64 / 2^32` 仍保留，这是协议解码，不属于猜测性归一化。

### P5 FIP TCP 解析性能和首样本诊断不足

旧问题：

- `struct.unpack(f'>{point_count}q', data_buff)` 会为 2,000,000 点包创建巨大 Python tuple，开销高。
- 日志只输出解析后范围，没有输出原始 int64 首值、原始 int64 范围和解码后首值。

修复：

- 改为 `np.frombuffer(data_buff, dtype=">i8")` 解析大端 int64，避免 Python tuple。
- 新增 `FIP_TCP_PARSE` 日志：输出 `raw_first`、`raw_range`、`decoded_first`、`decoded_range`。
- 新增 `FIP_TCP_FIRST_SAMPLE_ZERO` 日志：若 TCP 解码后首样本为 0，直接记录。

### P6 DAS slow_receive 日志误报

日志现象：

- DAS 每个包接收耗时约 1 s，日志大量输出 `TAB3_NODE das_tcp.slow_receive receive_ms≈1000`。
- 但当前包时长本身就是 1 s，接收完整 payload 接近 1 s 不等同于异常慢接收。

修复：

- `slow_receive` 阈值改为 `max(500 ms, packet_duration_seconds * 1500 ms)`。
- 1 s 包默认阈值为 1500 ms，正常 1 s 接收不再刷 warning。

## 4. 首点 0 的后续判定方法

本轮新增以下日志节点：

| 节点 | 含义 | 判定 |
|---|---|---|
| `FIP_TCP_FIRST_SAMPLE_ZERO` | TCP `<32,32>` 解码后首样本就是 0 | 说明发送端或原始包首点为 0 |
| `FIP_MAIN_FIRST_SAMPLE_ZERO` | Qt 分发到主程序后首样本仍为 0 | 说明 TCP 到主分发未改变首点 |
| `FIP_PROCESS_INPUT_FIRST_ZERO` | Tab1 处理线程分路后输入首点为 0 | 说明拆包后该路 FIP 首点为 0 |
| `FIP_PROCESS_UNFILTERED_FIRST_ZERO` | 相位展开后未滤波降采样首点为 0 | 说明未滤波 Tab3 源数据首点为 0 |
| `TAB3_NODE manager.fip_first_zero` | Tab3 manager 接收到的未滤波降采样首点为 0 | 说明进入 Tab3 对齐/存储前首点为 0 |
| `TAB3_NODE ui.fip_curve_first_zero` | UI 最终绘制数组首点为 0 | 说明实际显示首点为 0 |

复现后按上述节点逐层对比即可判断：

- 若最早出现 `FIP_TCP_FIRST_SAMPLE_ZERO`，首点 0 是原始 TCP 数据本身。
- 若 TCP 不为 0，但 `FIP_PROCESS_UNFILTERED_FIRST_ZERO` 开始为 0，问题在处理链。
- 若 manager 不为 0，但 UI 为 0，问题在绘图抽点或 UI 数据选择。
