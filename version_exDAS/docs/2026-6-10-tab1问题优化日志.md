## 背景

本日志记录 2026-06-10 对 Tab1 模块进行的系统性优化，问题来源为《当前版本软件 bug 分析总结》（`docs/2026-06-10-当前版本软件bug分析总结.md`）中 T1-01 至 T1-10 条目。

Tab1 主要线程结构如下：

```
主线程（Qt 事件循环）
  │  TCP data_received 信号
  ▼
DataProcessingThread     ─── input_queue ───► 处理后发 data_processed 信号
TimedomainPlotThread     ─── input_queue ───► 时域绘图
PSDPlotThread            ─── input_queue ───► PSD 绘图
DataStorageThread        ─── input_queue ───► 磁盘存储
```

各线程使用 `queue.Queue` 作为跨线程数据通道；绘图通过 `pyqtSignal` 回传主线程渲染。

## T1-01：每包 INFO 日志导致主线程高频 I/O

### 问题描述

`src/fip_tab1/fip_tcp_server.py` 的 `_process_data` 以及 `src/main.py` 的 `_process_data_packet` 在每个数据包到达时均打印 `INFO` 级日志。发送方以 5 Hz 固定频率发包，FileHandler 每秒执行 5 次以上磁盘写入，占用主线程时间片，导致 UI 响应延迟。

### 根本原因

`logging.basicConfig(level=logging.DEBUG)` 全局启用了 DEBUG 级别，加之调试期间在关键路径写入了逐包日志。

### 优化方案

1. `_setup_logging`：全局日志级别由 `DEBUG` 改为 `INFO`，消除开发阶段遗留的大量 DEBUG 输出。
2. `_process_data_packet`：删除无条件的逐包 INFO，改为每 50 包打印一次。
3. `_process_data`（TCP 服务器）：同样改为每 50 包打印一次接收日志。

### 修改文件

- `src/main.py`：`_setup_logging`、`_process_data_packet`
- `src/fip_tab1/fip_tcp_server.py`：`_process_data`

## T1-02：`_recv_exact` 不响应 `stop_server()`

### 问题描述

`OptimizedTCPServer._recv_exact` 在 `socket.timeout` 异常后无条件 `continue`，不检查 `_running` 标志。调用 `stop_server()` 后，`_recv_exact` 最长需等待 1 秒（`settimeout(1.0)` 的超时周期）才能检测到停止信号，导致线程退出缓慢。

### 根本原因

`socket.timeout` 分支只做了 `continue`，漏判停止条件。

### 优化方案

在 `socket.timeout` 分支中增加 `_running` 检查：

```python
except socket.timeout:
    # 超时后检查停止标志，确保 stop_server() 后能快速退出
    if not self._running:
        return None
    continue
```

- `src/fip_tab1/fip_tcp_server.py`：`_recv_exact`

## T1-03：非法包头导致字节流永久失步

### 问题描述

`_receive_loop` 在接收到非法 `data_length`（0 或 > 10,000,000）时执行 `continue`，跳过当前包但**不关闭连接**。由于 TCP 是字节流协议，非法包体的剩余字节仍留在缓冲区中，后续 `recv` 会将它们误当新的包头解析，导致后续所有包全部解析失败——即字节流**永久失步**。

### 根本原因

`continue` 只跳过了逻辑判断，没有消费掉非法包体，TCP 字节流的物理偏移未被纠正。

### 优化方案

将 `continue` 改为 `break`，关闭当前连接，由外层 `_server_loop` 等待新连接，从而重新建立字节流同步：

```python
if data_length == 0 or data_length > 10000000:
    self.logger.error(
        f"Invalid data_length={data_length} from {self.client_address}, "
        "closing connection to resync byte stream."
    )
    break
```

## T1-05：时域处理队列太小导致数据丢失

### 问题描述

`TimedomainPlotThread.input_queue` 初始容量为 10。发送方以 5 Hz 发包，若时域绘图线程处理稍慢（如刷新率不足或 GC 暂停），队列会在 2 秒内填满，导致包被丢弃。

### 根本原因

10 包的深度仅够缓冲 2 秒的突发，缓冲裕量不足。

### 优化方案

将队列容量扩大至 200，可缓冲 40 秒突发：

$$\text{内存} = 200 \times 20000 \times 8\ \text{字节} \approx 32\ \text{MB}$$

```python
self.input_queue = Queue(maxsize=200)
# 200 包 × 20000 样本/包 × 8 字节/样本 ≈ 32 MB，内存开销可接受
```

### 修改文件

- `src/fip_tab1/fip_tab1_manager.py`：`TimedomainPlotThread.__init__`

## T1-06：时域滑动窗口缓冲区使用 `list` 导致 $O(N)$ 开销

### 问题描述

`TimedomainPlotThread` 的 `data_buffer` 和 `time_buffer` 使用 Python `list`。每帧需要：

1. 追加新样本：$O(1)$ 均摊（`list.append`）
2. 裁剪旧样本：`_update_plot` 中 `keep_indices` 使用布尔索引，$O(N)$ 内存拷贝

当显示窗口为 10 s、采样率为 $100\ \text{kHz}$ 时，缓冲区最大 $10^6$ 条，每帧裁剪操作的时间复杂度为 $O(10^6)$，造成帧率严重下降。

### 根本原因

`list` 没有容量上限，累积到足够大时截断操作变为瓶颈；且 NumPy 布尔索引需要分配新数组，内存压力大。

### 优化方案

改用 `collections.deque(maxlen=N)`：

- `append` 时自动淘汰最旧元素，复杂度 $O(1)$
- 无需额外的截断/裁剪逻辑，消除 $O(N)$ 拷贝
- `maxlen` 随窗口时长动态调整

$$\text{maxlen} = \lceil \text{window\_duration} \times f_{\text{display}} \times 1.5 \rceil$$

其中 $1.5$ 倍系数作为缓冲裕量，防止偶发的多余数据超出边界。

`_update_plot` 简化为：

```python
def _update_plot(self):
    if len(self.time_buffer) == 0:
        return
    times_arr = np.array(self.time_buffer)
    values_arr = np.array(self.data_buffer)
    # 时间轴归零：以窗口第一个样本为原点
    times_rel = times_arr - times_arr[0]
    self.plot_ready.emit(times_rel, values_arr)
```

## T1-08：`add_raw_packet` 使用 `block=True` 阻塞主线程

### 问题描述

`DataStorageThread.add_raw_packet` 使用 `self.input_queue.put(packet, block=True)`。该方法在 Qt 主线程的信号槽调用链中被调用：

```
TCP data_received 信号（主线程）
  → _process_data_packet
    → tab1_manager.process_raw_packet
      → storage_thread.add_raw_packet  ← 阻塞点
```

若磁盘写入慢导致存储队列满，主线程将在此无限期阻塞，Qt 事件循环停止响应，造成**全局 UI 冻结**，同时阻断 TCP 接收，导致更大范围的数据丢失。

### 根本原因

`block=True` 是 `queue.Queue.put` 的默认值，在多线程服务端场景下是合理的；但在 Qt 主线程中调用时是致命的——主线程不允许执行任何阻塞操作。

### 优化方案

改为 `put_nowait`（等价于 `put(block=False)`），队列满时抛出 `Full` 异常，捕获后记录告警并丢包：

```python
def add_raw_packet(self, packet: RawDataPacket):
    """将原始数据包加入存储队列（主线程调用，必须非阻塞）。"""
    if not self.enabled:
        return
    if self._drain_mode:
        return
    try:
        self.input_queue.put_nowait(packet)
        self.stats['raw_packets_enqueued'] += 1
        self.stats['raw_queue_peak'] = max(
            self.stats['raw_queue_peak'], self.input_queue.qsize()
        )
    except Full:
        # 队列满：记录丢包，绝不阻塞主线程
        self.stats['storage_failure_count'] += 1
        self.logger.error(
            'Storage queue full (size=%d), dropping packet #%d. '
            'Disk may be too slow. Check storage_failure_count in stats.',
            self.RAW_QUEUE_MAXSIZE,
            packet.comm_count,
        )
```

**权衡**：队列满时丢包在磁盘严重过载时会发生，但这比全局冻结代价低得多。`storage_failure_count` 统计量可帮助运维人员检测磁盘瓶颈。

## T1-09：停止时存储队列中的尾部数据丢失

### 问题描述

原 `OptimizedTab1ThreadManager.stop()` 直接向所有线程发送 stop 信号并等待退出。若此时 `DataStorageThread.input_queue` 中还有未处理的包，`running=False` 会导致 `run` 循环立即退出，这些包**不会落盘**。

在正常工作会话结束时，最后几秒的数据可能因此丢失，导致存储文件在末尾截断。

### 优化方案

实现**两阶段停止**（流程图如下）：

```
stop() 调用
    │
    ▼
[阶段一] begin_drain()
    │   设置 _drain_mode=True
    │   add_raw_packet 不再接受新包
    │
    ▼
等待 storage_thread 排空队列（最多 10 s）
    │   _drain_mode=True 时 run 循环：
    │     - 检测到队列为空 → 执行 _flush_buffered_data() → 退出
    │     - get(timeout=0.2) 超时且队列空 → 同上
    │
    ▼
[阶段二] 向所有线程发送 stop()
    │
    ▼
等待各线程退出（最多 3 s）
    │
    ▼
重置 _drain_mode=False（为下次启动准备）
```

关键代码（`run` 循环中）：

```python
while self.running:
    self._process_ctrl_commands()
    try:
        if self._drain_mode and self.input_queue.empty():
            self.logger.info('Storage drain complete, exiting run loop')
            break
        packet = self.input_queue.get(timeout=0.2)
        ...
    except Empty:
        if self._drain_mode:
            self.logger.info('Storage drain complete (timeout), exiting run loop')
            break
        continue
self._flush_buffered_data()
```

### 修改文件

- `src/fip_tab1/fip_tab1_manager.py`：`DataStorageThread.begin_drain`、`DataStorageThread.run`、`OptimizedTab1ThreadManager.stop`

## T1-10：`set_enabled` 多线程竞争条件

### 问题描述

原 `DataStorageThread.set_enabled` 直接从 UI 线程修改 `self.enabled` 并调用 `_flush_buffered_data()` 和 `_clear_buffer()`：

```python
def set_enabled(self, enabled: bool):
    self.enabled = enabled        # UI 线程写
    if not enabled:
        self._flush_buffered_data()  # UI 线程操作缓冲区
        self._clear_buffer()         # UI 线程清空缓冲区
```

与此同时，`DataStorageThread.run` 也在读写 `buffered_requests`（`_append_request`、`_save_completed_chunks`）。两线程同时操作同一个 `list` 对象，存在竞争条件，可能导致：

- `buffered_requests` 数据损坏
- 文件写入内容不完整
- 偶发 `IndexError`

### 根本原因

Python 的 `list` 操作不是线程安全的（GIL 仅保护单条字节码，复合操作不安全）。

### 优化方案

引入控制命令队列 `_ctrl_queue`（`queue.Queue`，线程安全），将 `set_enabled` 改为发送命令，由存储线程在包边界串行处理：

```python
# UI 线程（生产者）
def set_enabled(self, enabled: bool):
    self._ctrl_queue.put_nowait({'cmd': 'set_enabled', 'value': enabled})

# 存储线程（消费者，在 run() 中每次循环开头调用）
def _process_ctrl_commands(self):
    while True:
        try:
            cmd = self._ctrl_queue.get_nowait()
            if cmd['cmd'] == 'set_enabled':
                new_enabled = cmd['value']
                if self.enabled == new_enabled:
                    continue
                self.enabled = new_enabled
                if not new_enabled:
                    self._flush_buffered_data()
                    self._clear_buffer()
                    self.logger.info('Storage disabled, buffer flushed and cleared')
                else:
                    self.logger.info('Storage enabled')
        except Empty:
            break
```

这样缓冲区的所有修改都在存储线程中完成，不再有竞争。
