## 问题排序

### S1 操作或参数问题，跳过程序修复

问题：

1. FIP TCP 多次收到 `data_length=16000000`，而当前程序阈值拒绝该包长，共 19 条 `ERROR`。
2. DAS TCP 绑定了本机不存在或不可用的 IP，导致 `[WinError 10049]`，DAS 服务启动失败 2 次，并引发主控 Tab3 启动失败 2 次。

结论：这两类问题来自联调参数、发送端程序或本机 IP 选择，不属于当前软件逻辑缺陷。本轮未改 FIP TCP 包长阈值，也未改 DAS 绑定策略。

### S2 Tab3 绘图卡顿和鼠标短时无响应，已修复

问题：

1. 用户反馈 Tab3 波形刷新时偶发卡几秒，鼠标也会短时无响应。
2. 旧日志没有 `DASPlotWorker`、Tab3 UI `setData`、Space-Time `setImage` 的逐帧耗时日志，因此无法直接从旧日志定位具体哪一帧阻塞。
3. 代码静态检查发现三个高风险卡顿点：
   - `update_tab3_fip_curve()` 每个 FIP 包都在 Qt 主线程绘制约 40000 点 FIP 对比曲线。
   - `DASPlotWorker._build_space_time_payload()` 每包对历史矩阵做 `np.concatenate(blocks, axis=1)`，显示窗口越大，重复拷贝越多。
   - `update_tab3_plot_payload()` 每帧执行 `ImageItem.setImage()` 后又调用色标和直方图范围更新，容易阻塞 Qt 事件循环。

解决方案：

1. 参照 `E:\codes\PCIe-7821\pcie7821_gui` 中 Tab2 Time-Space 图和 Tab1 phase 时域图的更新机制，将 Tab3 Space-Time 改为固定大小 `float32` 滚动显示缓存。
2. `DASPlotWorker` 不再每包拼接全部历史矩阵，只把最新 DAS block 追加到滚动 buffer，超过窗口后左移并覆盖旧列。
3. Tab3 UI 增加刷新限频：FIP 对比曲线最小刷新间隔 `0.4 s`，DAS 曲线和 Space-Time 最小刷新间隔 `0.2 s`。
4. Tab3 曲线进入 `setData()` 前统一限制到最多 `12000` 点；Space-Time 显示矩阵限制到最多约 `300000` 像素。
5. Space-Time 每帧只更新图像本体和必要的 `rect`；色标、`Vmin/Vmax` 和 Histogram 范围改为由参数变更时更新，不再每帧重设。
6. PyQtGraph 曲线继续启用 `setClipToView(True)`、自动 peak downsampling 和 `setSkipFiniteCheck(True)` 的快速路径。

涉及文件：

- `src/das_tab3/das_plot_worker.py`
- `src/ui/main_window.py`
- `src/das_tab3/das_tab3_manager.py`

### S3 FIP 性能日志 `Rate` 字段误导延时判断，已修复

问题：

旧日志中 `Performance Stats` 的 `Rate` 从 `2.7 pkt/s` 持续上升到 `640.1 pkt/s`。按相邻性能日志时间差复算，每 50 包间隔平均 `10.000 s`，真实包率平均 `5.001 pkt/s`，范围 `4.897-5.110 pkt/s`。因此旧 `Rate` 字段是累计包数除以最近一个统计间隔，公式错误，不代表真实通信速率。

解决方案：

1. `OptimizedTCPServer` 增加 `_stats_packets_at_last_log`。
2. 性能日志改为用当前统计间隔内的包数计算 `packet_rate`。
3. 新连接时同步重置 `_stats_packets_at_last_log`，避免跨会话污染。

涉及文件：

- `src/fip_tab1/fip_tcp_server.py`

### S5 Tab2 触发存储排空超时，已梳理，按要求暂不修复排空算法

问题：

日志末尾出现 1 条 `WARNING`：`Tab2 storage drain timeout: some trigger events may not have been saved.`

原因梳理：

1. Tab2 触发存储需要等待告警事件后的 `post_trigger_seconds` 数据窗口。
2. 停机时日志显示 `pending=1`，说明仍有一个触发保存请求在等待后触发窗口。
3. 如果此时采集停止或等待时间不足，存储线程会持续等待 `_latest_time` 追上目标窗口，最终触发 5 秒排空超时。
4. 可选修复方向是停机时保存已采集到的部分后触发数据，并在 `.npz` 元数据中标注是否完整；但用户已明确要求先跳过、不修复。

已执行的相关修复：

1. 在 Tab2 左侧参数区顶部新增总控按钮 `Start Tab2`。
2. 按钮默认未选中，因此默认不启动 Tab2。
3. 主程序增加 Tab2 开关守卫：未开启时不启动 Tab2 线程，不把 Tab1 处理后的数据转发给 Tab2。
4. 运行中关闭按钮时，如果 Tab2 正在运行，则停止 Tab2 管线并清空 Tab2 特征图。

涉及文件：

- `src/ui/main_window.py`
- `src/main.py`

### S6 日志文件编码未显式指定，已修复

问题：Windows 下 `logging.FileHandler` 未显式指定编码时会使用系统默认编码。按 UTF-8 读取历史日志时，中文系统错误信息会显示为替换字符，影响后续日志分析。

解决方案：`src/main.py` 中 `logging.FileHandler(...)` 统一指定 `encoding='utf-8'`，并支持 `python run.py --log FILE` 指定日志文件。

说明：历史日志中已经写入的乱码无法自动恢复；本修复保证后续新日志按 UTF-8 写入。
