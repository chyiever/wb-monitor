## Tab1 (FIP) – 通信与流畅性深度分析

### 2.1 线程架构说明

Tab1 采用"原始包双路分发"架构（自 2026-04-29 起）：

```
RawDataPacket
├── DataProcessingThread  → 绘图链路（允许丢旧包）
└── DataStorageThread     → 存储链路（阻塞等待，不丢包）
```

总体思路合理：绘图优先实时性，存储优先完整性。但以下细节存在重大隐患。

---

### 2.2 TCP 通信层问题

**问题 T1-01：全局日志级别为 DEBUG，生产环境严重影响性能（卡顿根因之一）**

- **位置**：`src/main.py:112`

```python
logging.basicConfig(level=logging.DEBUG, ...)
```

- **危害**：每包触发大量 DEBUG 日志（主线程每包 INFO + 多处 DEBUG），5 Hz × 多条 = 每秒数十次 FileHandler I/O。Python FileHandler 无内置异步缓冲，每次写盘约 0.1–0.5 ms，加之 `main.py:348` 每包都打 INFO，合计可使主线程 Qt 事件循环每包额外消耗 1–3 ms，长期累积导致 UI 卡顿，在慢存储盘场景下尤为明显。
- **严重性**：**高**

---

**问题 T1-02：`_recv_exact` 在 `socket.timeout` 时无法快速响应 stop 信号**

- **位置**：`src/fip_tab1/fip_tcp_server.py:236–248`

```python
while bytes_needed > 0 and self._running:
    try:
        chunk = self.client_socket.recv(chunk_size)
        ...
    except socket.timeout:
        continue   # bytes_needed 不变，循环继续，等待下一次超时
```

- **危害**：若客户端在发送数据中途停止但未断连，`recv` 每秒超时一次，`_running=True` 时永不退出。调用 `stop_server()` 后需等最多 1 秒（超时间隔）线程才能退出。若 UI 停止按钮后 3 s（wait 超时）线程仍未结束，会被强制截断，存在 socket 句柄残留风险。
- **严重性**：中

---

**问题 T1-03：大包场景使用 `TCP_NODELAY` 效果有限**

- **位置**：`src/fip_tab1/fip_tcp_server.py:135`
- **分析**：每包 $200000 \times 8 = 1.6\text{ MB}$，TCP 自动分段传输，`TCP_NODELAY` 仅对小包低延迟有意义，对大包反而会增加 ACK 数量和系统调用开销，略微增加 CPU 负担。
- **严重性**：低

### 2.3 数据流与丢包分析

#### 绘图链路（DataProcessingThread）

**计算：1 MHz 时绘图处理线程是否积压？**

每包主要处理步骤及估算耗时（CPython，标准 PC）：

| 步骤 | 数据量 | 估算耗时 |
|------|-------:|-------:|
| `np.unwrap` 相位展开 | 200 000 点 | 2–5 ms |
| `sosfilt` 4 阶滤波 | 200 000 点 | 3–8 ms |
| `decimate` 降采样 ×5（含 AA 滤波） | 200 000 → 40 000 点 | 2–5 ms |
| 构造 ProcessedData + 信号发射 | — | < 1 ms |
| **合计** | | **7–19 ms** |

包间隔 $T_{packet} = 1/5 = 200\text{ ms}$，**正常情况处理线程不积压**。

但注意：DataProcessingThread 是 `QThread`（操作系统线程），NumPy C 扩展执行期间会释放 GIL，GIL 争用风险较低。若系统有其他 CPU 密集型进程，调度抢占导致单包处理偶发延迟 > 200 ms 时，队列短暂积压，因有 100 包缓冲，最多容忍约 20 s 的积压不丢包。

---

**问题 T1-04：时域绘图队列极小（maxsize=10），容易丢绘图帧**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:207`

```python
self.input_queue = Queue(maxsize=10)
```

- **危害**：若主线程 Qt 事件循环短暂繁忙（如同时处理用户交互、菜单操作），`plot_ready` 信号堆积，下一包到来时队列满，静默丢弃，用户看到**波形更新停止或跳帧**，可能误判为软件死机。
- **严重性**：中

---

**问题 T1-05：时域缓冲区用 Python `list` 逐元素遍历，大时间窗口时性能急剧下降**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:352–366`

```python
keep_indices = [i for i, t in enumerate(self.time_buffer) if t >= cutoff_time]
```

- **分析**：显示窗口 1 s、100 kHz 显示采样率时缓冲约 100 000 元素，单次遍历约 5–15 ms（CPython），每秒一次，尚可接受。但若用户将 `window_duration` 调大至 30 s，缓冲膨胀至 300 万点，单次遍历约 150 ms，绘图线程本身被卡住，UI 画面更新严重滞后。
- **严重性**：中（随窗口长度线性恶化）

---

**问题 T1-06：PSD 线程队列极小（maxsize=5），长窗口 PSD 计算时画面停止更新**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:386`

```python
self.input_queue = Queue(maxsize=5)
```

- **分析**：PSD 每 5 包计算一次（约 1 次/秒）。默认窗口 0.4 s × 200 kHz = 80 000 点时：

$$nperseg = \min\!\left(\frac{80000}{8},\; 200000,\; 50000\right) = 10000$$

单次 Welch 约需 **10–30 ms**，正常可接受。

但若用户设置 `psd_window_duration = 2\text{ s}`，累积 400 000 点：

$$nperseg = 50000\text{（硬上限）}$$

单次 Welch 约需 **50–100 ms**，超过更新节奏，队列迅速堆满，PSD 画面几乎停止更新。

- **严重性**：中

#### 存储链路（DataStorageThread）

**问题 T1-07：存储入队 `block=True` 在主线程调用，将导致软件卡死 ⚠️**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:511`

```python
self.input_queue.put(packet, block=True)  # ← 主线程调用！
```

完整调用链：

```
TCP data_received 信号（Qt queued connection，主线程槽）
→ _process_data_packet()                          [main.py:339]
→ tab1_manager.process_raw_packet()               [fip_tab1_manager.py:892]
→ storage_thread.add_raw_packet()                 [fip_tab1_manager.py:499]
    → self.input_queue.put(packet, block=True)    [← 此处阻塞主线程]
```

**卡死量化分析**：

存储线程每包处理时间 = 相位展开（约 5–10 ms） + npz 写盘（SSD 约 10–50 ms，机械盘 50–200 ms）

设存储线程单包处理时间为 $T_{store}$，包间隔为 $T_{packet} = 200\text{ ms}$：

- 若 $T_{store} < T_{packet}$：存储线程消化速度 > 到达速度，队列不积压，主线程不阻塞。
- 若 $T_{store} > T_{packet}$：每秒净积压 $\approx \frac{T_{store} - T_{packet}}{T_{packet}} \times 5$ 包/s，约经过：

$$t_{卡死} = \frac{2000\text{ 包}}{净积压速率} \text{ 秒}$$

后队列满，`put(block=True)` **将主线程无限期阻塞**，UI 完全冻结。

以机械硬盘（$T_{store} \approx 250\text{ ms}$）为例，净积压约 0.25 包/s，约 **2.2 小时**后卡死。若并发磁盘 I/O（如同时录制 DAS），更快触发。

- **危害**：软件卡死，键鼠无响应，数据从卡死时刻起全部丢失
- **严重性**：**严重（可复现的卡死 Bug）**

### 2.4 1 MHz 高采样率同时开启时域绘图 + PSD + 本地存储时的综合风险

| 组件 | 单包处理时间 | 包间隔 | 积压风险 | 影响 |
|------|------------:|-------:|:-------:|------|
| DataProcessingThread | 7–19 ms | 200 ms | 极低 | 无 |
| TimedomainPlotThread | 5–15 ms（小窗口） | 200 ms | 低 | 丢绘图帧 |
| PSDPlotThread | 10–100 ms（视窗口） | 200 ms | 低–中 | PSD 画面滞后 |
| DataStorageThread | 55–210 ms（视磁盘） | 200 ms | **高（机械盘）** | **主线程阻塞卡死** |
| 主线程 UI | 1–3 ms（正常）| 200 ms | 低 | 被存储入队阻塞 |

**三个核心问题的明确回答**：

1. **当前线程架构和数据流会不会导致丢数（存储）？**
   - SSD 场景：不丢，存储链路有 2000 包缓冲且 block=True 确保入队。
   - 机械盘场景：长时间运行后主线程被阻塞卡死，**卡死后所有新到包均丢失**。

2. **1 MHz 时，同时开启时域绘图 + PSD + 本地存储，软件会不会卡死？**
   - SSD：大概率不卡，但 DEBUG 日志开启时 UI 有轻微卡顿。
   - 机械盘：**会卡死**，触发时间取决于磁盘速度，机械盘约数分钟至数小时。

3. **存下来的数据会不会丢部分数据包？**
   - 正常运行期间：存储链路独立于绘图链路，绘图丢帧不影响存储，**不丢包**。
   - 主线程卡死后：队列已满，新包从卡死时刻起全部丢失。
   - 相位展开失败时：有 fallback 机制（使用 wrapped phase），**不丢包但数据精度下降**。

### 2.5 存储数据正确性问题

**问题 T1-08：存储降采样未施加抗混叠滤波，导致频谱折叠**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:575`

```python
storage_data = np.asarray(unwrapped[::self.STORAGE_DOWNSAMPLE_FACTOR], dtype=np.float64)
```

- **分析**：对 1 MHz 展开相位数据直接 ×5 抽取，输出 200 kHz。奈奎斯特频率 $f_N = 100\text{ kHz}$，原始信号中频率 $f \in (100\text{ kHz},\; 500\text{ kHz})$ 的成分将折叠：

$$f_{alias} = \left| f - n \cdot f_s' \right|, \quad f_s' = 200\text{ kHz}, \quad n = 1, 2, \ldots$$

而绘图链路在降采样前已施加带通低通滤波（截止 $\leq 10\text{ kHz}$），实质上已完成抗混叠。存储链路未做同样处理，两路数据频谱不一致，存储数据高频部分失真。

- **严重性**：中（信号保真度）

---

**问题 T1-09：存储文件 `timestamp` 字段为相对秒偏移，易被误用为绝对时间**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:724`

```python
timestamp = self.saved_sample_count / sample_rate if sample_rate > 0 else 0.0
```

- **危害**：该字段值为 `0.0, 2.0, 4.0, ...`（会话内秒偏移），形似 Unix 时间戳，实为相对时间。真实绝对时间在 `data_info['stream_start_time']` 中。若分析脚本直接以 `timestamp` 字段做绝对时间对齐，结果严重错误。
- **严重性**：中

---

**问题 T1-10：chunk 切分时边界包的 comm_count 在相邻文件元数据中重复出现**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:670–689`
- **分析**：当一个原始包被切分（部分写入当前 chunk，余量留入下一 chunk）时，`end_comm_count` 指向该包，下一个文件的 `start_comm_count` 也从该包开始。若分析工具以闭区间 `[start_comm_count, end_comm_count]` 查找包范围，边界包会被重复计算。
- **严重性**：低

### 2.6 相位展开与信号处理问题

**问题 T1-11：相位范围判断条件 `np.max(np.abs(phase_data)) > 5` 存在边缘歧义**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:149` 和 `:563`

```python
if np.max(np.abs(phase_data)) > 5:
    phase_data = phase_data / np.pi
```

- **分析**：该逻辑假设"最大绝对值 > 5 意味着数据单位是 rad，需除以 $\pi$ 归一化到 $[-1, 1]$"。但：
  - TCP 接收的 float64（`int64 / 2^32`）值域约 $[-2, 2]$，正常不超过 5，判断正确。
  - **问题在于**：相位展开后的累积相位可能达到数百甚至数千弧度，若此处理意外被应用于展开后数据，会将累积相位错误缩小 $\pi$ 倍，导致后续分析严重错误。

  当前代码只在 `DataProcessingThread._process_packet` 和 `DataStorageThread._build_storage_request` 两处使用，均在处理原始 `packet.phase_data`，理论上不会处理展开后数据。但逻辑不够健壮，缺乏显式断言或注释，维护时易引入错误。
- **严重性**：中

---

**问题 T1-12：`PhaseUnwrapper.reset()` 与 `unwrap_phase()` 之间无锁保护**

- **位置**：`src/processing/phase_unwrap.py:176–178`（reset）和 `:81–87`（unwrap）
- **分析**：`reset()` 在主线程调用（`_start_monitoring`），`unwrap_phase()` 在 `DataProcessingThread` 中调用。两者并发时若 reset 将 `_last_phase = None` 后，处理线程刚好读取并通过 `_last_phase is not None` 检查的旧值计算偏移，可能导致首包相位连续性计算出错（偏移计算基于已无效的旧尾相位）。
- **严重性**：低（竞争窗口极短，约微秒级）

## Tab2 (FIP 检测) 问题分析

**问题 T2-01：Tab2 与绘图链路共享处理结果，绘图丢包等于检测丢包**

- **位置**：`src/main.py:325`

```python
self.tab1_manager.data_processor.data_processed.connect(
    self.fip_tab2_manager.process_processed_data)
```

- **分析**：`DataProcessingThread` 队列满时优先丢弃旧包（绘图优先策略），Tab2 共享该信号，同样丢包。检测算法需要连续信号片段进行特征提取（短时能量、峭度、有效值等），丢包会导致：
  - 特征计算窗口出现空洞，统计量偏低
  - 检测阈值判断可能漏报断丝事件

  Tab1 存储链路已建立独立原始包路径（2026-04-29 优化），**Tab2 应同样建立独立接收路径**以保证检测完整性。
- **严重性**：中

**问题 T2-02：`stop()` 中 3 秒超时可能截断未完成的触发存储**

- **位置**：`src/fip_tab2/fip_tab2_manager.py:51–56`

```python
self.detection_worker.flush_active_event()
for worker in ...:
    worker.stop()
for worker in ...:
    worker.wait(3000)  # ← 硬截断
```

- **分析**：`flush_active_event()` 将活跃事件推入存储队列，但随即以 3 秒超时强制等待。若触发存储写盘（机械盘大文件）需 > 3 s，会被截断，导致触发事件文件不完整。
- **严重性**：低

## Tab3 (eDAS) 问题分析

**问题 T3-01：`_storage_timer` 回调在主线程执行，可能周期性阻塞 UI**

- **位置**：`src/das_tab3/das_tab3_manager.py:36–39`

```python

self._storage_timer.setInterval(1000)

```

- **分析**：`QTimer` 的回调在主线程 Qt 事件循环驱动，若 `_maybe_store_snapshot` 包含磁盘写入或大块 numpy 数据处理，每秒执行一次会导致 UI 短暂冻结（10–200 ms），用户感知为界面卡顿。
- **严重性**：中

**问题 T3-02：FIP 与 DAS 对齐依赖包速率稳定，长期运行可能累积时序漂移**

- **分析**：FIP 以 5 Hz 向 Tab3 报送对齐时间戳，若 TCP 传输存在抖动（网络拥塞、GIL 延迟），FIP 包到达时刻偏差不反映在 `comm_count` 中，而对齐算法依赖 `comm_count × 0.2s` 作为时间基准。实际到达延迟与标称时间的偏差会使 FIP-DAS 对齐产生毫秒至百毫秒级误差，长时间运行后误差累积影响联合分析。
- **严重性**：中（对联合定位准确性有影响）

## 跨模块问题

**问题 X-01：各线程统计信息无 UI 展示入口，现场问题难以定位**

- **分析**：`get_thread_stats()` 返回处理线程和存储线程的队列峰值、丢包数、相位展开失败数等关键指标，但 UI 中无任何控件展示，现场联调时无法实时判断哪个环节出现积压或丢包，问题定位全靠日志文件，效率极低。
- **严重性**：低（可观测性不足）

---

**问题 X-02：所有线程使用软停止（标志位），快速重启时存在短暂资源竞争**

- **分析**：`stop()` 仅设置 `running=False`，线程在 `queue.get(timeout=0.1–0.5)` 超时后才退出，最长响应约 0.5 s。若用户在点击"停止"后立即再次点击"开始"，新线程可能与旧线程短暂并存，共享同一个 `Queue` 对象（因新 `OptimizedTab1ThreadManager` 是重新创建的，共享问题不存在），但 TCP server 的旧 socket 可能尚未关闭，导致端口绑定失败（`Address already in use`）。
- **严重性**：低（快速重启场景偶发）

## 修复优先级建议

### P0 – 立即修复（可复现的卡死 / 严重数据错误）

**P0-1：将存储入队改为非阻塞，彻底消除主线程阻塞（解决 T1-07）**

修复方案（最简，保守丢包）：

```python
# src/fip_tab1/fip_tab1_manager.py
def add_raw_packet(self, packet: RawDataPacket):
    if not self.enabled:
        return
    try:
        self.input_queue.put_nowait(packet)
        self.stats['raw_packets_enqueued'] += 1
        self.stats['raw_queue_peak'] = max(
            self.stats['raw_queue_peak'], self.input_queue.qsize())
    except Full:
        self.stats['storage_failure_count'] += 1
        self.logger.error(
            'Storage queue full, dropping packet #%d to avoid blocking main thread',
            packet.comm_count)
```

如希望完全不丢包，可在主线程和存储线程之间引入一个轻量调度线程，专门做 `block=True` 的转发，主线程只做 `put_nowait`。

在 `_build_storage_request` 中，相位展开后先低通再抽取：

```python
# 抗混叠截止频率 = 输出奈奎斯特 = STORAGE_SAMPLE_RATE / 2
from scipy.signal import sosfilt, butter
_cutoff_norm = 0.8 / self.STORAGE_DOWNSAMPLE_FACTOR  # 归一化截止频率，留 20% 安全裕量
_aa_sos = butter(8, _cutoff_norm, output='sos')
filtered = sosfilt(_aa_sos, unwrapped)
storage_data = filtered[::self.STORAGE_DOWNSAMPLE_FACTOR].astype(np.float64)
```
