## T2-02：停止时 3 秒超时截断触发事件存储

### 问题描述

`FIPTab2Manager.stop()` 调用 `detection_worker.flush_active_event()` 将活跃告警事件推入存储请求队列后，立即以 3 秒超时强制等待所有线程退出。若触发存储包含大文件写盘（机械盘 NPZ 写入 > 3 s），`FIPTriggerStorageWorker` 会被强制截断，导致触发事件的 NPZ 文件不完整，分析时无法加载。

### 根本原因

原 `stop()` 没有给存储线程足够的时间完成最后一个写盘任务；`FIPTriggerStorageWorker.run()` 也没有排空机制，`running=False` 后直接退出，不处理队列中剩余的存储请求。

### 优化方案

实现两阶段停止：

```
flush_active_event()
       │
       ▼
begin_drain()              ← 存储线程进入排空模式
       │  run 循环继续处理三个队列中已有内容
       │  以及 _pending_requests 中等待后触发窗口的请求
       │  所有请求处理完毕后自行退出
       ▼
等待排空完成（最多 5 s）
       │  轮询 has_pending_work()
       ▼
stop() 所有线程 → wait(3 s)
```

新增方法：

- `FIPTriggerStorageWorker.begin_drain()`：设置 `_drain_mode=True`，run 循环在排空后自行退出
- `FIPTriggerStorageWorker.has_pending_work()`：返回三个队列和 `_pending_requests` 是否全空
- `FIPTriggerStorageWorker.reset_state()`：新增重置 `_drain_mode=False`

### 修改文件

- `src/fip_tab2/fip_trigger_storage.py`：`run`、`stop`、`begin_drain`（新增）、`has_pending_work`（新增）、`reset_state`
- `src/fip_tab2/fip_tab2_manager.py`：`stop`（新增 `import time` + 两阶段停止逻辑）

## T2-03：丢包后时间轴仍连续，导致跨缺口错误特征窗口

### 问题描述

`FIPFeatureWorker._process_packet` 按收到的样本数构造时间轴，不检查 `comm_count` 缺口。丢包时，缺口两侧的数据会被连续拼入同一滑动窗口参与特征计算，可能产生：

- 虚假的能量峰值（缺口两侧相位不连续形成冲激）→ 误报告警
- 缺口期间真实声音信号的窗口范围计算错误 → 漏检

同时，滤波器状态跨缺口传播，使缺口两侧的滤波瞬态相互污染。

### 优化方案

在 `_process_packet` 的采样率检查之后，加入 `comm_count` 连续性检测：

```python
if self._last_comm_count is not None and packet.comm_count != self._last_comm_count + 1:
    # 检测到缺口：清空信号缓冲区，重置滤波器状态
    self._stream_time_origin += (self._stream_sample_index / self.sample_rate)
    self._stream_sample_index = 0
    self._signal_buffer = np.array([], dtype=np.float64)
    self._buffer_start_sample_index = 0
    self._next_window_start_index = 0
    self._zi = None  # 重置滤波器，阻断瞬态污染
self._last_comm_count = packet.comm_count
```

**时间轴修正**：将时间原点推进到缺口后当前包的理论起始时间，保证后续特征帧时间戳大致准确：

$$t_{\text{origin}}^{\text{new}} = t_{\text{origin}}^{\text{old}} + \frac{N_{\text{processed}}}{f_s}$$

其中 $N_{\text{processed}}$ 为缺口前已累积的样本数，$f_s$ 为当前采样率。

### 修改文件

- `src/fip_tab2/fip_feature_worker.py`：`__init__`（新增 `_last_comm_count`）、`reset_state`（重置 `_last_comm_count`）、`_process_packet`（新增缺口检测）

## T3-01：`QTimer` 存储快照回调在主线程直接写盘，周期性卡顿

### 问题描述

`DASTab3Manager._maybe_store_snapshot` 由 `QTimer`（主线程）每秒触发，内部调用 `np.savez_compressed` 执行磁盘写入。联合存储文件包含 FIP 和 DAS 的多帧数据，大小约数 MB，每秒一次磁盘写入在主线程执行，导致 UI 每秒出现约 10–200 ms 的卡顿。

### 优化方案

新建 `DASStorageWorker`（独立 `QThread`），将写盘操作完全移出主线程：

```
主线程 QTimer (1 s)
  │  _maybe_store_snapshot()  ← 仅做 O(1) 的 put_nowait，无 I/O
  │  封装 DASStorageRequest(frames, output_dir, end_comm)
  │  enqueue_request(request)
  ▼
DASStorageWorker.run()   ← 独立后台线程
  │  input_queue.get(timeout=0.2)
  ▼
DASStorageWorker._save(request)
  ▼  np.savez_compressed(file_path, **payload)
```

`DASStorageWorker` 队列满时覆写最旧请求（写盘跟不上时优先保证内存不增长），并记录 `requests_dropped` 告警。

### 修改文件

- `src/das_tab3/das_storage_worker.py`：**新建文件**，包含 `DASStorageRequest` 和 `DASStorageWorker`
- `src/das_tab3/das_tab3_manager.py`：导入新类；`__init__` 创建 `storage_worker`；`start/stop` 启停线程；`_maybe_store_snapshot` 改为仅做 `enqueue_request`

## T3-02：联合存储文件大量重叠，写放大严重

### 问题描述

原 `_maybe_store_snapshot` 每秒调用 `coordinator.get_recent_frames(interval_seconds)` 获取最近 N 秒全量快照。若 `interval_seconds = 10 s`，则每次保存约 50 帧（5 Hz × 10 s），相邻文件之间约有 49 帧（98%）重叠，每秒写 2 × 50 帧数据 ≈ 10 倍写放大。

### 优化方案

新增 `AlignedSessionCoordinator.get_frames_since(last_comm_count)` 方法，仅返回 `comm_count > last_comm_count` 的新增帧：

```python
def get_frames_since(self, last_comm_count: int) -> List[AlignedPacketFrame]:
    """返回 comm_count 严格大于 last_comm_count 的所有对齐帧（增量获取）。"""
    with self._lock:
        new_counts = [c for c in self._ordered_counts if c > last_comm_count]
        frames = [self._build_frame_locked(c) for c in new_counts]
    return frames
```

`_maybe_store_snapshot` 改为调用此方法，每次仅写入上次结束后的新增帧，相邻文件之间无重叠，写放大降为 1 倍。存储的 NPZ 文件增加 `incremental=True` 标记，与旧的全量快照文件区分。

**写放大对比**：

| 方式 | 每秒写帧数 | 写放大比 |
|------|----------:|-------:|
| 原全量快照（interval=10s） | $5 \times 10 = 50$ | $\approx 10\times$ |
| 新增量 chunk（1s 触发） | $5 \times 1 = 5$ | $1\times$ |

### 修改文件

- `src/alignment/aligned_session_coordinator.py`：新增 `get_frames_since`
- `src/das_tab3/das_tab3_manager.py`：`_maybe_store_snapshot` 调用 `get_frames_since`

## T3-03：FIP/DAS 对齐仅检查 online 状态，不验证真实时序

### 问题描述

原 `_derive_alignment_status` 逻辑：两路 `_fip_online` 和 `_das_online` 均为 `True` 即返回 `"aligned"`。但两路数据使用不同的时序基准（FIP 为会话内归一化 `comm_count`，DAS 为原始计数），且 TCP 传输抖动会导致两路数据的到达时刻存在偏差。若偏差累积，实际上两路数据在时间轴上已错位，但系统仍显示 `"aligned"`，误导后续联合分析。

### 优化方案

在两路均在线时，额外比较最新 `comm_count` 的绝对差值：

$$\Delta_{\text{comm}} = \left| \text{comm\_count}_{\text{FIP}} - \text{comm\_count}_{\text{DAS}} \right|$$

若 $\Delta_{\text{comm}} > 5$（即偏差超过约 1 秒的包），返回新状态 `"lagging"` 而非 `"aligned"`：

```python
MAX_COMM_COUNT_DRIFT = 5  # 5 包 ≈ 1 s

def _derive_alignment_status(self) -> str:
    ...
    if self._fip_online and self._das_online:
        if (self._last_fip_comm_count is not None
                and self._last_das_comm_count is not None):
            drift = abs(self._last_fip_comm_count - self._last_das_comm_count)
            if drift > self.MAX_COMM_COUNT_DRIFT:
                return "lagging"
        return "aligned"
    ...
```

同时在 `_emit_status` 的 payload 中增加 `comm_count_drift` 字段，供 UI 展示实时偏差值辅助诊断。

**注意**：这是对齐质量的必要但不充分条件——`comm_count` 相等不代表物理时钟同步，仅代表两路数据在逻辑上处于同一包序号。完整的时钟同步验证需要额外的 PTP/IRIG 硬件支持，超出当前软件范围。

### 修改文件

- `src/alignment/aligned_session_coordinator.py`：`MAX_COMM_COUNT_DRIFT`（新增类常量）、`_derive_alignment_status`（新增偏差检查）、`_emit_status`（新增 `comm_count_drift` 字段）

## T1-15：缺包后 `PhaseUnwrapper` 沿用旧状态，跨缺口相位错误连续化

### 问题描述

`DataProcessingThread._process_packet` 使用 `PhaseUnwrapper.unwrap_phase()` 跨包连续展开相位，依赖 `_last_phase` 记录上一包末尾相位值。当发生缺包（`comm_count` 不连续）时，展开器仍以旧 `_last_phase` 为锚点，对新包第一个样本做 $2\pi$ 偏移连续化，将缺口期间的相位漂移误读为真实信号（产生虚假阶跃），影响后续滤波和特征提取。

### 优化方案

在 `_process_packet` 中加入缺口检测，缺口时调用 `phase_unwrapper.reset()`：

```python
# DataProcessingThread.__init__
self._last_comm_count: Optional[int] = None

# DataProcessingThread._process_packet
if (self._last_comm_count is not None
        and packet.comm_count != self._last_comm_count + 1):
    self.logger.warning(
        'comm_count gap: last=%d, current=%d, missing=%d. Resetting phase unwrapper.',
        self._last_comm_count, packet.comm_count,
        packet.comm_count - self._last_comm_count - 1,
    )
    self.phase_unwrapper.reset()
    self.stats['gap_count'] += 1
self._last_comm_count = packet.comm_count
```

### 修改文件

- `src/fip_tab1/fip_tab1_manager.py`：`DataProcessingThread.__init__`（新增 `_last_comm_count`、`gap_count`）、`_process_packet`（新增缺口检测）

```python
def update_storage_path(self, path: str):
    """?????????"""

def update_storage_interval(self, interval_seconds: float):
```

```python
def update_storage_path(self, path: str):
```

## X-02：快速重启时 TCP 端口短暂被旧 socket 占用

### 问题描述

`stop_server()` 后旧 socket 进入 `TIME_WAIT` 状态，立即重启时 `bind()` 可能抛出 `OSError: [Errno 98] Address already in use`，导致启动失败且错误提示不够明确（用户不知道原因是端口占用）。

### 优化方案

在 `start_server()` 中将 `bind()` 封装为最多重试 3 次（间隔 1 s）的逻辑，最终失败时给出详细错误提示：

```python
for attempt in range(1, 4):
    try:
        self.server_socket.bind((self.ip, self.port))
        break
    except OSError as bind_err:
        if attempt < 3:
            self.logger.warning("Port %d bind failed (attempt %d/3), retrying...", ...)
            time.sleep(1.0)
        else:
            raise OSError(
                f"Port {self.port} still occupied after 3 attempts. "
                "Please wait and retry."
            ) from bind_err
```

`SO_REUSEADDR` 已在原代码中设置，通常足以解决 `TIME_WAIT` 问题；重试机制作为保底措施。
