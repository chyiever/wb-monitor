# 2026-08-18 eDAS模块联调前潜在bug和风险排查与修复报告

## 一、排查范围

本次排查同时阅读了两个项目的通信、显示、对齐和存储链路：

- 本软件 `wb-monitor`：`src/das/`、`src/alignment/`、`src/ui/main_window.py`、`src/main.py`、近期 FIP 联调日志和 `docs/dev_log.md`。
- eDAS 采集软件 `E:\codes\PCIe-7821\pcie7821_gui`：`src/tcp_tab3/`、`src/config.py`、近期大数据量显示/存储优化日志和测试。

联调目标数据量按用户给定参数估算：

- 时间采样率：100 kHz
- 位置点：800
- 每秒数值量：`100000 * 800 = 80,000,000`
- 当前 TCP 协议载荷类型：big-endian `float64`
- 满速 1 s TCP payload：`80,000,000 * 8 = 640,000,000 bytes`，约 610 MiB

这意味着 eDAS 若不在发送端做时间/空间降采样，单包、接收缓存、对齐缓存、绘图队列和存储队列都必须按 600 MiB 级别设计，不能再用“包数”作为唯一容量限制。

## 二、总体结论

FIP 侧近期优化已经基本解决了 FIP-only 采集存储的主要软件瓶颈：TCP/处理链连续、FIP2 有效、存储写放大已去除、关闭窗口尾包排空已补齐。剩余 FIP1 全 0 属硬件/采集通道问题，不是本软件解析或存储格式问题。

eDAS 联调前发现 4 个高优先级软件风险：

1. **P0：eDAS 接收端 512 MiB payload 上限低于满速 1 s 数据包**。100 kHz x 800 x float64 的 1 s 包约 610 MiB，旧上限会直接判为非法包。
2. **P0：eDAS TCP 断开或坏头后接收循环可能继续按错误字节边界解析**。旧逻辑在 header/payload 读取失败时 `continue`，客户端断开时可能反复读空；坏 header 后继续读下一 header 会把 payload 当 header，造成流错位。
3. **P0：eDAS 绘图、原始存储和对齐缓存按包数限流，在 610 MiB/包场景会出现 GB 到百 GB 级内存膨胀**。旧默认 eDAS 原始存储队列 200 包，理论上超过 120 GiB。
4. **P0：eDAS 发送端 `comm_count` 在发送成功后才递增，会掩盖网络/发送队列丢包，造成 FIP/eDAS 假对齐**。如果网络未连接或发送失败，旧逻辑丢弃采集块但不消耗序号，接收端看不到缺包，后续联合分析会误以为同序号同时间。

本次已完成代码修复，并通过编译、模拟 TCP 链路、字节预算自检和 eDAS 发送端单元测试。

## 三、已修复问题

### P0-1：eDAS满速包被接收端拒收

涉及文件：`src/das/tcp_server.py`

原因：

- 本软件 `DASTCPServer.MAX_PAYLOAD_BYTES` 原为 `512 * 1024 * 1024`。
- 100 kHz x 800 x float64 x 1 s 为约 610 MiB，超过旧上限。

修复：

- 将上限提升到 `1024 * 1024 * 1024`，保证 1 s 满速 eDAS 包可被协议层接收。
- 保留上限保护，避免明显异常 header 触发无界内存申请。

影响：

- 可以接收满速 1 s eDAS 包。
- 这不代表建议长期按 610 MiB/包直接做联合压缩存储；显示和存储仍需按下面策略限流。

### P0-2：断开/坏包后的TCP流错位与空读循环

涉及文件：`src/das/tcp_server.py`

原因：

- `_recv_exact()` 返回空时旧逻辑 `continue`，客户端已断开时接收循环不会及时退出。
- header 合法性校验失败后旧逻辑继续读下一 header，但坏 header 后面的 payload 仍在 TCP 流里，继续读会把 payload 前 24 字节误当成新 header。

修复：

- header 读取失败、payload 读取失败时立即跳出当前客户端接收循环，关闭连接状态并等待重连。
- header 字段非法或 `data_bytes` 非法时关闭连接以重新同步 TCP 字节流。
- `_recv_exact()` 返回 `bytearray`，payload 转 NumPy 时对 big-endian float64 做原地 byteswap，避免 `bytes()` 和 `astype()` 对大 payload 形成额外整包拷贝。

收益：

- 断线后不会出现空读死循环。
- 坏包后不会继续错位解析。
- 610 MiB 级 payload 的瞬时内存峰值降低约一份整包拷贝。

### P0-3：绘图队列按包数限流导致内存膨胀

涉及文件：`src/das/plot_worker.py`

原因：

- 旧绘图队列 `Queue(maxsize=4)` 在小包场景合理，但满速 eDAS 下 4 包约 2.4 GiB。
- `display_seconds=1.0` 时旧历史裁剪用 `packet_end_time >= cutoff_time`，边界上会多保留前一秒整包，满速下额外多占约 610 MiB。

修复：

- 绘图队列新增 `768 MiB` 字节预算，超过预算时丢弃旧显示帧，只保留最新可显示帧。
- 历史裁剪边界从 `>= cutoff_time` 改为 `> cutoff_time`，1 s 窗口不再保留刚好落在窗口左边界之外的整包。

设计原则：

- 绘图是可降级链路，可以跳旧帧保实时。
- 存储和通信完整性不能依赖绘图队列，因此绘图丢帧只影响屏幕刷新，不改变 eDAS 原始存储队列。

### P0-4：eDAS原始存储队列按包数限流导致百GB级风险

涉及文件：`src/das/storage_worker.py`

原因：

- 旧 `EDASRawStorageWorker.INPUT_QUEUE_MAXSIZE = 4096`，UI 默认 eDAS 队列 200 包。
- 满速 1 s 包约 610 MiB，200 包理论上约 122 GiB，极易触发换页并拖慢磁盘，最终导致更多丢包。

修复：

- eDAS 原始存储队列新增 `2048 MiB` 字节预算。
- 入队时同时检查用户配置包数上限和字节预算；超过任一限制时丢弃最旧待写包，记录 `queued_mb / incoming_mb / budget_mb`。
- 统计新增 `queue_peak_bytes`，便于现场日志判断是否碰到字节预算。

影响：

- 内存不会因存储队列无限膨胀。
- 如果磁盘持续低于输入速率，仍会丢旧包；这是正确的降级行为。长期完整保存 640 MB/s 需要足够快的 NVMe 和优先使用 eDAS raw `.bin` 存储。

### P1-1：FIP/eDAS对齐缓存和联合npz存储写放大

涉及文件：

- `src/alignment/aligned_session_coordinator.py`
- `src/das/manager.py`
- `src/das/storage_worker.py`

原因：

- 对齐缓存旧逻辑只按 `cache_seconds` 保留帧。满速 eDAS 下 10 s 缓存约 6.1 GiB，仅 DAS 矩阵就很大。
- 联合 `.npz` 若一次写入 10 s DAS raw matrix，压缩期间会产生巨大 CPU/内存/磁盘压力。

修复：

- `AlignedSessionCoordinator` 增加 `max_cache_bytes`，默认 `2048 MiB`，按“时间窗口”和“字节预算”共同裁剪。
- `DASTab3Manager._maybe_store_snapshot()` 在缓存因字节预算接近上限时允许提前 flush 较短联合 chunk，避免一直达不到 10 s interval 而永远不落盘。
- `DASStorageRequest` 增加 `estimated_bytes`。
- `DASStorageWorker` 对联合存储队列增加 `2048 MiB` 字节预算；单次联合请求超过 `2048 MiB` 时拒绝写入并向 UI 报错，提示缩短联合间隔、发送端降采样或改用 eDAS raw 存储。
- eDAS 停止时后台存储线程等待时间从 5 s 延长到 180 s，减少关闭窗口/停止通信时的尾包丢失。

边界：

- 满速 eDAS 原始数据不适合长期写入压缩 `.npz` 联合文件。联合 `.npz` 更适合降采样后的分析快照或短窗口；完整 eDAS 应使用 raw `.bin`。

### P0-5：eDAS发送端comm_count假对齐

涉及项目：`E:\codes\PCIe-7821\pcie7821_gui`

涉及文件：

- `src/tcp_tab3/tcp_types.py`
- `src/tcp_tab3/tcp_tab3_manager.py`
- `src/tcp_tab3/tcp_sender_worker.py`
- `tests/test_tcp_tab3_comm_count.py`

原因：

- 旧实现由 `TCPSenderWorker` 在 `sendall()` 成功后递增 `_comm_count`。
- 如果网络未连接、发送失败或发送队列丢旧包，被丢弃的采集块不会消耗序号。
- 接收端看到的 eDAS `comm_count` 仍然连续，但实际采集时间已经跳过，FIP/eDAS 会出现假对齐。

修复：

- `PhaseQueueItem` 增加 `comm_count`。
- `TCPTab3Manager._append_comm_frames()` 在采集帧聚合成通信包时立即分配并递增 `_next_comm_count`。
- `TCPSenderWorker` 构包时使用 `item.comm_count`，不再在发送成功后递增内部序号。
- 新增测试验证连续形成的通信包序号为 `[0, 1, 2]`，与发送队列是否后续丢旧包无关。

收益：

- 网络断开、重连或发送队列丢旧包后，接收端能通过 `comm_count` 缺口看到真实 eDAS 数据缺失。
- FIP/eDAS 联合对齐不会被连续但错误的 eDAS 序号误导。

## 四、优先级与后续现场复测建议

### P0 必测项

1. eDAS 发送端在本软件启动监听后再启动采集，确认接收端日志出现连续 `DAS TCP server started`、`DAS client connected`、`das_tcp.packet`。
2. 满速或接近满速测试时观察：
   - `Invalid DAS data_bytes` 不应出现。
   - `DAS comm_count gap` 应只在真实网络/发送队列丢包时出现。
   - `Alignment cache byte budget trimming active` 如果出现，说明已触发大包缓存保护。
   - `storage.edas_enqueue ... queued_mb` 不应无限增长。
3. eDAS raw 存储开启后观察：
   - `storage.edas_slow`
   - `eDAS raw storage queue full`
   - `.json` 元数据中 `comm_counts` 是否连续。
4. FIP/eDAS 同时启动后观察：
   - `alignment_status=aligned`
   - `comm_count_drift <= 5`
   - FIP/eDAS 同序号接收时间差是否稳定，而不是持续漂移。

### P1 建议项

1. 满速 eDAS 下不要默认开启 10 s 联合 `.npz` 原始矩阵存储；优先使用 eDAS raw `.bin`，联合 `.npz` 只存降采样分析窗口。
2. 如果需要联合原始数据，建议先把 eDAS 发送端 `time_downsample` 或 `space_downsample` 调到使单包 payload 小于 256 MiB，再做长时间复测。
3. 现场记录磁盘型号、目标盘剩余空间和持续写入速度。640 MB/s 原始保存对普通 SATA SSD 或机械盘不现实。

### P2 已知非软件问题

1. FIP1 通道近期日志显示全程 `INT64_MIN`，经修复后存储为全 0，仍需检查 FIP1 传感器、采集通道或采集软件侧使能。
2. FIP2 近期 5 分钟复测已显示存储连续，建议继续做 30 分钟以上 FIP+eDAS 同时运行验证。

## 六、结论

本次修复后，本软件在 eDAS 联调前具备更稳健的底层保护：

- 满速 1 s eDAS 包不会因 512 MiB 上限被直接拒收。
- TCP 断开和坏包不会造成错位解析。
- 绘图、eDAS 原始存储、联合存储、对齐缓存均有字节级内存保护。
- 停止 eDAS 时会更充分等待存储排空。
- eDAS 发送端 `comm_count` 能反映真实采集包序号，FIP/eDAS 对齐不再被网络丢包掩盖。

仍需强调：100 kHz x 800 x float64 是 640 MB/s 级链路。软件可以避免内存失控和假对齐，但无法用队列弥补长期磁盘吞吐不足。现场联调应优先验证 raw `.bin` 持续写速、发送端降采样策略和同序号时间差稳定性。
