# 2026-04-29 Tab1 原始包独立存储与线程统计补充说明

## 1. 背景

在当前 `Tab1 / FIP` 主链路已经具备实时接收、处理、绘图和存储能力的基础上，本次本地改动主要针对两个问题继续优化：

- 绘图处理链路和存储链路复用同一份处理结果，存储精度和稳定性受绘图节奏影响
- 缺少线程级运行统计，难以定位队列积压、丢包、乱序和相位展开失败等问题

本次修改集中在：

- `src/fip_tab1/fip_tab1_manager.py`

核心目标是：

- 将 Tab1 存储路径从“处理后分发”改为“原始包独立入队”
- 让存储线程自行完成相位展开和固定倍率降采样
- 为处理线程和存储线程补充可观测统计信息
- 增强存储链路对缺包、乱序、回退和阻塞的诊断能力

## 2. 本次改动概览

本地未上传代码的实际功能变化主要有 4 类：

1. `DataProcessingThread` 队列扩容，并增加处理链路统计
2. `DataStorageThread` 从“接收 StorageRequest”改为“直接接收 RawDataPacket”
3. `OptimizedTab1ThreadManager` 改为把原始包同时分发给“绘图处理线程”和“存储线程”
4. 新增 `get_thread_stats()`，可统一返回处理线程和存储线程运行统计

## 3. DataProcessingThread 改动

### 3.1 队列容量调整

`DataProcessingThread` 的输入队列上限由原先的较小容量调整为：

```python
INPUT_QUEUE_MAXSIZE = 100
```

对应行为仍然保持“服务绘图优先”的策略：

- 队列满时丢弃最旧包
- 优先接纳最新到达的数据包

这说明该线程仍然定位为“面向实时绘图的处理路径”，目标是尽量保证界面跟随最新数据，而不是绝对无损。

### 3.2 增加处理线程统计

处理线程新增统计字段：

- `queue_maxsize`
- `queue_peak`
- `packets_enqueued`
- `packets_processed`
- `queue_drop_count`
- `processing_failure_count`
- `phase_unwrap_failure_count`

并新增：

```python
get_stats()
```

用于导出当前线程统计结果。

### 3.3 行为上的实际影响

这部分改动不会改变 Tab1 绘图主功能，但会带来两个实际效果：

- 更容易确认实时绘图是否因队列堆积而丢包
- 更容易区分“绘图慢”与“相位展开失败/处理异常”

## 4. DataStorageThread 改动

## 4.1 存储输入从处理结果改为原始包

本次最关键的功能变化是：

- 旧逻辑：`DataStorageThread` 接收 `StorageRequest`
- 新逻辑：`DataStorageThread` 直接接收 `RawDataPacket`

也就是说，存储线程不再依赖 `DataProcessingThread` 已经处理好的 `ProcessedData.unwrapped_data`，而是走独立原始包路径。

对应接口由：

```python
add_storage_request(...)
```

改为：

```python
add_raw_packet(...)
```

这意味着：

- 绘图链路和存储链路正式解耦
- 绘图线程丢包不再直接等价于存储线程丢包
- 存储可以按自身节奏消费原始数据

### 4.2 存储线程内部自行完成相位展开

新增 `_build_storage_request()`，在存储线程内部完成：

1. 原始相位归一化判断
2. 相位展开
3. 固定 `5x` 降采样
4. 构造用于落盘的 `StorageRequest`

这使得存储链路的数据来源更明确：

```text
RawDataPacket
-> 相位展开
-> 5x 降采样
-> phase_unwrapped_downsampled
-> NPZ 存储
```

### 4.3 存储线程改为“尽量不丢包”

存储线程新增：

```python
RAW_QUEUE_MAXSIZE = 2000
```

并且在队列满时采用：

- 记录告警
- 阻塞等待入队

而不是像绘图线程那样主动丢弃旧包。

这说明存储路径和绘图路径采用了不同设计目标：

- 绘图路径：优先实时性，允许丢旧包
- 存储路径：优先数据完整性，尽量保留所有原始包

### 4.4 增加缺包 / 乱序 / 重复包检测

存储线程新增了基于 `comm_count` 的链路诊断能力，会记录：

- `raw_packets_missing`
- `raw_packets_duplicate_or_out_of_order`

检测逻辑包括：

- 当前包号比上一个包号大于 1，判定中间有缺包
- 当前包号小于或等于上一个包号，判定为重复包或乱序包

这部分统计对于判断 TCP 接收链路、发送端重连或中间缓存异常很有用。

### 4.5 增加相位展开失败回退

在存储线程中，如果相位展开失败，不再直接放弃当前包，而是：

- 记录 `phase_unwrap_failure_count`
- 打告警日志
- 使用 wrapped phase 的回退数据继续存储

这样做的效果是：

- 存储链路容错性更强
- 单个包相位展开异常时，不会直接造成整段存储中断

### 4.6 增加存储统计

存储线程新增统计字段：

- `raw_queue_maxsize`
- `raw_queue_peak`
- `raw_packets_enqueued`
- `raw_packets_processed`
- `raw_packets_missing`
- `raw_packets_duplicate_or_out_of_order`
- `enqueue_wait_count`
- `phase_unwrap_failure_count`
- `storage_failure_count`
- `saved_file_count`
- `saved_sample_count`

并新增：

```python
get_stats()
```

用于输出存储线程当前统计状态。

## 5. Tab1ThreadManager 改动

### 5.1 原始包双路分发

`OptimizedTab1ThreadManager.process_raw_packet()` 现在会把同一个 `RawDataPacket` 同时送到两个路径：

1. `DataProcessingThread`
2. `DataStorageThread`

也就是：

```text
RawDataPacket
-> 绘图处理线程
-> 存储线程
```

而不是旧逻辑中的：

```text
RawDataPacket
-> 绘图处理线程
-> ProcessedData
-> 生成 StorageRequest
-> 存储线程
```

### 5.2 删除存储依赖处理结果的逻辑

原先 `_distribute_processed_data()` 中会把：

```python
processed_data.unwrapped_data[::5]
```

包装成 `StorageRequest` 后再交给存储线程。

这部分逻辑现在已经删除，说明：

- `_distribute_processed_data()` 只负责给时域绘图和 PSD 绘图分发
- 存储不再依赖绘图链路处理结果

### 5.3 新增线程统计统一出口

`OptimizedTab1ThreadManager` 新增：

```python
get_thread_stats()
```

返回：

- `processing`
- `storage`

两类统计信息，方便后续 UI、日志或调试接口直接读取。

## 6. 对当前功能的实际影响

本次本地未上传改动带来的功能变化，可以概括为以下几点：

### 6.1 存储链路更独立

存储不再依赖绘图线程的处理结果，降低了绘图卡顿、绘图丢包对存储结果的直接影响。

### 6.2 存储链路更偏向“保数据”

通过更大的原始包队列和阻塞等待机制，存储线程更倾向于保留数据，而不是为追实时性主动丢包。

### 6.3 更容易诊断现场问题

新增统计后，可以更直接回答这些问题：

- 绘图线程是否积压
- 绘图线程是否丢包
- 存储线程是否等待过
- 存储链路是否出现缺包
- 是否有重复包、乱序包
- 相位展开是否频繁失败

### 6.4 存储结果的来源更清晰

当前存储文件仍然是：

- 相位展开后的数据
- 固定 `5x` 降采样
- `200 kHz`
- `.npz`

但这些数据现在来自“存储线程独立处理原始包”，而不是“复用绘图路径输出”。

## 8. 结论

这次本地未上传代码并不是新增一个新的 Tab 或新的 UI 功能，而是对 `Tab1` 底层链路做了一次很明确的工程化增强：

1. 绘图处理路径继续保持实时优先
2. 存储路径改为原始包独立处理，强调完整性优先
3. 处理线程和存储线程都补充了统计信息
4. 存储线程新增了缺包、乱序、阻塞和相位展开失败的可观测能力

从工程效果上看，这次修改的重点不是“界面新增了什么”，而是“Tab1 的采集、处理、存储链路更可诊断、更稳、更适合现场联调”。
