## Tab1 (FIP) – 通信与流畅性深度分析

### 2.1 线程架构说明

Tab1 采用"原始包双路分发"架构（自 2026-04-29 起）：

```
RawDataPacket
├── DataProcessingThread  → 绘图链路（允许丢旧包）
└── DataStorageThread     → 存储链路（阻塞等待，不丢包）
```

总体思路合理：绘图优先实时性，存储优先完整性。但以下细节存在重大隐患。

---

### 2.2 TCP 通信层问题

**问题 T1-01：全局日志级别为 DEBUG，生产环境严重影响性能（卡顿根因之一）**

- **位置**：`src/main.py:112`

```python
logging.basicConfig(level=logging.DEBUG, ...)
```

- **危害**：每包触发大量 DEBUG 日志（主线程每包 INFO + 多处 DEBUG），5 Hz × 多条 = 每秒数十次 FileHandler I/O。Python FileHandler 无内置异步缓冲，每次写盘约 0.1–0.5 ms，加之 `main.py:348` 每包都打 INFO，合计可使主线程 Qt 事件循环每包额外消耗 1–3 ms，长期累积导致 UI 卡顿，在慢存储盘场景下尤为明显。
- **严重性**：**高**

---

**问题 T1-02：`_recv_exact` 在 `socket.timeout` 时无法快速响应 stop 信号**

- **位置**：`src/fip_tab1/fip_tcp_server.py:236–248`

```python
while bytes_needed > 0 and self._running:
    try:
        chunk = self.client_socket.recv(chunk_size)
        ...
    except socket.timeout:
        continue   # bytes_needed 不变，循环继续，等待下一次超时
```

- **危害**：若客户端在发送数据中途停止但未断连，`recv` 每秒超时一次，`_running=True` 时永不退出。调用 `stop_server()` 后需等最多 1 秒（超时间隔）线程才能退出。若 UI 停止按钮后 3 s（wait 超时）线程仍未结束，会被强制截断，存在 socket 句柄残留风险。
- **严重性**：中

---

**问题 T1-03：非法协议头导致 TCP 字节流失步**

- **位置**：`src/fip_tab1/fip_tcp_server.py:183–197`

```python
# 遇到非法 data_length 直接 continue，没有关闭连接或重新同步
if data_length <= 0 or data_length > MAX_EXPECTED_LENGTH:
    continue
```

- **危害**：一次坏头后，后续接收到的包体数据持续被错误地当作包头解析，造成字节流永久失步。直到连接断开重建前，所有后续数据均为乱码。
- **严重性**：**高**

---

**问题 T1-04：大包场景使用 `TCP_NODELAY` 效果有限**

- **位置**：`src/fip_tab1/fip_tcp_server.py:135`
- **分析**：每包 $200000 \times 8 = 1.6\text{ MB}$，TCP 自动分段传输，`TCP_NODELAY` 仅对小包低延迟有意义，对大包反而会增加 ACK 数量和系统调用开销，略微增加 CPU 负担。
- **严重性**：低

---

### 2.3 数据流与丢包分析

#### 绘图链路（DataProcessingThread）

**计算：1 MHz 时绘图处理线程是否积压？**

每包主要处理步骤及估算耗时（CPython，标准 PC）：

| 步骤 | 数据量 | 估算耗时 |
|------|-------:|-------:|
| `np.unwrap` 相位展开 | 200 000 点 | 2–5 ms |
| `sosfilt` 4 阶滤波 | 200 000 点 | 3–8 ms |
| `[::5]` 降采样（抽点） | 200 000 → 40 000 点 | < 1 ms |
| 构造 ProcessedData + 信号发射 | — | < 1 ms |
| **合计** | | **6–15 ms** |

包间隔 $T_{packet} = 1/5 = 200\text{ ms}$，**正常情况处理线程不积压**。

但注意：DataProcessingThread 是 `QThread`（操作系统线程），NumPy C 扩展执行期间会释放 GIL，GIL 争用风险较低。若系统有其他 CPU 密集型进程，调度抢占导致单包处理偶发延迟 > 200 ms 时，队列短暂积压，因有 100 包缓冲，最多容忍约 20 s 的积压不丢包。

---

**问题 T1-05：时域绘图队列极小（maxsize=10），容易丢绘图帧**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:207`

```python
self.input_queue = Queue(maxsize=10)
```

- **危害**：若主线程 Qt 事件循环短暂繁忙（如同时处理用户交互、菜单操作），`plot_ready` 信号堆积，下一包到来时队列满，静默丢弃，用户看到**波形更新停止或跳帧**，采集期间发生的声音信号可能在实时波形中不可见，可能误判为软件死机。
- **严重性**：**高**（违反"显示波形连续"要求）

---

**问题 T1-06：时域缓冲区用 Python `list` 逐元素遍历，大时间窗口时性能急剧下降**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:352–366`

```python
keep_indices = [i for i, t in enumerate(self.time_buffer) if t >= cutoff_time]
```

- **分析**：显示窗口 1 s、100 kHz 显示采样率时缓冲约 100 000 元素，单次遍历约 5–15 ms（CPython），每秒一次，尚可接受。但若用户将 `window_duration` 调大至 30 s，缓冲膨胀至 300 万点，单次遍历约 150 ms，绘图线程本身被卡住，UI 画面更新严重滞后。
- **严重性**：中（随窗口长度线性恶化）

---

**问题 T1-07：PSD 线程队列极小（maxsize=5），长窗口 PSD 计算时画面停止更新**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:386`

```python
self.input_queue = Queue(maxsize=5)
```

- **分析**：PSD 每 5 包计算一次（约 1 次/秒）。默认窗口 0.4 s × 200 kHz = 80 000 点时：

$$nperseg = \min\!\left(\frac{80000}{8},\; 200000,\; 50000\right) = 10000$$

单次 Welch 约需 **10–30 ms**，正常可接受。

但若用户设置 `psd_window_duration = 2\text{ s}`，累积 400 000 点：

$$nperseg = 50000\text{（硬上限）}$$

单次 Welch 约需 **50–100 ms**，超过更新节奏，队列迅速堆满，PSD 画面几乎停止更新。

- **严重性**：中

---

#### 存储链路（DataStorageThread）

**问题 T1-08：存储入队 `block=True` 在主线程调用，将导致软件卡死 ⚠️**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:511`

```python
self.input_queue.put(packet, block=True)  # ← 主线程调用！
```

完整调用链：

```
TCP data_received 信号（Qt queued connection，主线程槽）
→ _process_data_packet()                          [main.py:339]
→ tab1_manager.process_raw_packet()               [fip_tab1_manager.py:892]
→ storage_thread.add_raw_packet()                 [fip_tab1_manager.py:499]
    → self.input_queue.put(packet, block=True)    [← 此处阻塞主线程]
```

**卡死量化分析**：

存储线程每包处理时间 = 相位展开（约 5–10 ms） + npz 写盘（SSD 约 10–50 ms，机械盘 50–200 ms）

设存储线程单包处理时间为 $T_{store}$，包间隔为 $T_{packet} = 200\text{ ms}$：

- 若 $T_{store} < T_{packet}$：存储线程消化速度 > 到达速度，队列不积压，主线程不阻塞。
- 若 $T_{store} > T_{packet}$：每秒净积压 $\approx \frac{T_{store} - T_{packet}}{T_{packet}} \times 5$ 包/s，约经过：

$$t_{卡死} = \frac{2000\text{ 包}}{净积压速率} \text{ 秒}$$

后队列满，`put(block=True)` **将主线程无限期阻塞**，UI 完全冻结。

以机械硬盘（$T_{store} \approx 250\text{ ms}$）为例，净积压约 0.25 包/s，约 **2.2 小时**后卡死。若并发磁盘 I/O（如同时录制 DAS），更快触发。

**内存风险附注**：存储队列最大 2000 包 × 1.6 MB/包 = **3.2 GB** 的原始数组可驻留在内存中（不含派生数组）。在队列积压期间内存持续增长，可能提前触发 OOM 导致进程崩溃，早于预计的卡死时间点。

- **危害**：软件卡死，键鼠无响应，数据从卡死时刻起全部丢失
- **严重性**：**严重（可复现的卡死 Bug）**

---

**问题 T1-09：停止监测时未排空存储队列，尾部数据确定丢失**

- **位置**：`src/fip_tab1/fip_tab1_manager.py`（DataStorageThread.run + OptimizedTab1ThreadManager.stop）

- **分析**：调用 `stop()` 后，DataStorageThread 在检测到 `_running=False` 后立即结束循环，仍在 `input_queue` 中等待处理的原始包不会被处理。管理器仅等待线程 3 秒后继续执行关闭逻辑，无任何排空确认。每次正常停止均会丢失队列尾部数据，包数约等于停止时队列中积压的包数。
- **严重性**：**高**（每次停止都确定丢失尾包）

---

**问题 T1-10：运行中调用 `set_enabled(False)` 存在数据丢失与线程竞争**

- **位置**：`src/fip_tab1/fip_tab1_manager.py`（DataStorageThread.set_enabled 与 run 循环）

- **分析**：从 UI 线程调用 `set_enabled(False)` 时，存储线程随后取到的包因 `enabled=False` 被直接 `continue` 跳过，队列中已入队但尚未处理的包全部丢失。UI 线程还可能同时刷新和清空缓冲区，与存储线程产生并发写竞争。
- **严重性**：中

### 2.4 1 MHz 高采样率同时开启时域绘图 + PSD + 本地存储时的综合风险

| 组件 | 单包处理时间 | 包间隔 | 积压风险 | 影响 |
|------|------------:|-------:|:-------:|------|
| DataProcessingThread | 6–15 ms | 200 ms | 极低 | 无 |
| TimedomainPlotThread | 5–15 ms（小窗口） | 200 ms | 低 | 丢绘图帧（违反连续显示要求） |
| PSDPlotThread | 10–100 ms（视窗口） | 200 ms | 低–中 | PSD 画面滞后 |
| DataStorageThread | 55–210 ms（视磁盘） | 200 ms | **高（机械盘）** | **主线程阻塞卡死** |
| 主线程 UI | 1–3 ms（正常）| 200 ms | 低 | 被存储入队阻塞 |

**三个核心问题的明确回答**：

1. **当前线程架构和数据流会不会导致丢数（存储）？**
   - SSD 场景：正常运行期间不丢，存储链路有 2000 包缓冲且 block=True 确保入队。但**每次停止监测都会丢失尾包**（T1-09）。
   - 机械盘场景：长时间运行后主线程被阻塞卡死，**卡死后所有新到包均丢失**（T1-08）。

2. **1 MHz 时，同时开启时域绘图 + PSD + 本地存储，软件会不会卡死？**
   - SSD：大概率不卡，但 DEBUG 日志开启时 UI 有轻微卡顿。
   - 机械盘：**会卡死**，触发时间取决于磁盘速度，机械盘约数分钟至数小时。

3. **存下来的数据会不会丢部分数据包？**
   - 正常运行期间：存储链路独立于绘图链路，绘图丢帧不影响存储，**不丢包**。
   - 主线程卡死后：队列已满，新包从卡死时刻起全部丢失。
   - 停止监测时：队列尾包确定丢失（T1-09）。
   - 相位展开失败时：有 fallback 机制（使用 wrapped phase），**不丢包但数据精度下降**。

### 2.5 存储数据正确性问题

**问题 T1-11：存储 `timestamp` 字段为相对秒偏移，易被误用为绝对时间**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:724`

```python
timestamp = self.saved_sample_count / sample_rate if sample_rate > 0 else 0.0
```

- **危害**：该字段值为 `0.0, 2.0, 4.0, ...`（会话内秒偏移），形似 Unix 时间戳，实为相对时间。真实绝对时间在 `data_info['stream_start_time']` 中。若分析脚本直接以 `timestamp` 字段做绝对时间对齐，结果严重错误。
- **严重性**：中

---

**问题 T1-12：chunk 切分时边界包的 comm_count 在相邻文件元数据中重复出现**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:670–689`
- **分析**：当一个原始包被切分（部分写入当前 chunk，余量留入下一 chunk）时，`end_comm_count` 指向该包，下一个文件的 `start_comm_count` 也从该包开始。若分析工具以闭区间 `[start_comm_count, end_comm_count]` 查找包范围，边界包会被重复计算。
- **严重性**：低

---

**问题 T1-13：`comm_count` 归一化隐藏原始序号，断连/复位场景难以溯源**

- **分析**：`_normalize_comm_count()` 在发送端计数回退时自动重新建立基准，归一化后的 `comm_count` 对 UI 友好，但最终存储文件不保留原始 `raw_comm_count`。若发生断连重连或发送端复位，新会话的 `comm_count` 从 0 重新开始，与前一会话无法区分，难以判断两段数据是否连续。
- **严重性**：中

---

### 2.6 相位展开与信号处理问题

**问题 T1-14：相位范围判断条件 `np.max(np.abs(phase_data)) > 5` 存在边缘歧义**

- **位置**：`src/fip_tab1/fip_tab1_manager.py:149` 和 `:563`

```python
if np.max(np.abs(phase_data)) > 5:
    phase_data = phase_data / np.pi
```

- **分析**：该逻辑假设"最大绝对值 > 5 意味着数据单位是 rad，需除以 $\pi$ 归一化到 $[-1, 1]$"。但相位展开后的累积相位可能达到数百甚至数千弧度，若此处理意外被应用于展开后数据，会将累积相位错误缩小 $\pi$ 倍，导致后续分析严重错误。当前代码仅在处理原始 `packet.phase_data` 时使用，理论上不会出错，但逻辑不够健壮，缺乏显式断言，维护时易引入错误。
- **严重性**：中

---

**问题 T1-15：缺包后 `PhaseUnwrapper` 沿用旧状态，跨缺口相位可能错误连续**

- **位置**：`src/processing/phase_unwrap.py`（`unwrap_phase` 与 `_last_phase`）
- **分析**：`PhaseUnwrapper` 用 `_last_phase` 保持跨包连续性，但当发现 `comm_count` 不连续（缺包）时，不重置展开状态。缺口两侧的数据会被强行用 $2\pi$ 偏移连续化，产生错误的相位跳变，可能将缺包期间的相位漂移误读为真实信号。
- **严重性**：中

---

**问题 T1-16：`PhaseUnwrapper.reset()` 与 `unwrap_phase()` 之间无锁保护**

- **位置**：`src/processing/phase_unwrap.py:176–178`（reset）和 `:81–87`（unwrap）
- **分析**：`reset()` 在主线程调用（`_start_monitoring`），`unwrap_phase()` 在 `DataProcessingThread` 中调用。两者并发时若 reset 将 `_last_phase = None` 后，处理线程刚好读取并通过 `_last_phase is not None` 检查的旧值计算偏移，可能导致首包相位连续性计算出错（偏移计算基于已无效的旧尾相位）。
- **严重性**：低（竞争窗口极短，约微秒级）

## Tab2 (FIP 检测) 问题分析

**问题 T2-01：Tab2 与绘图链路共享处理结果，绘图丢包等于检测丢包**

- **位置**：`src/main.py:325`

```python
self.tab1_manager.data_processor.data_processed.connect(
    self.fip_tab2_manager.process_processed_data)
```

- **分析**：`DataProcessingThread` 队列满时优先丢弃旧包（绘图优先策略），Tab2 共享该信号，同样丢包。检测算法需要连续信号片段进行特征提取（短时能量、峭度、有效值等），丢包会导致：
  - 特征计算窗口出现空洞，统计量偏低
  - 检测阈值判断可能漏报断丝事件

  Tab1 存储链路已建立独立原始包路径（2026-04-29 优化），**Tab2 应同样建立独立接收路径**以保证检测完整性。
- **严重性**：中（违反"通信获取数据连续完整"要求）

---

**问题 T2-02：停止时 3 秒超时可能截断未完成的触发存储**

- **位置**：`src/fip_tab2/fip_tab2_manager.py:51–56`

```python
self.detection_worker.flush_active_event()
for worker in ...:
    worker.stop()
for worker in ...:
    worker.wait(3000)  # ← 硬截断
```

- **分析**：`flush_active_event()` 将活跃事件推入存储队列，但随即以 3 秒超时强制等待。若触发存储写盘（机械盘大文件）需 > 3 s，会被截断，导致触发事件文件不完整。
- **严重性**：低

**问题 T2-03：丢包后时间轴仍连续，可能产生错误窗口和误报**

- **位置**：`src/fip_tab2/fip_feature_worker.py`（时间轴构造）
- **分析**：`FIPFeatureWorker` 按收到的样本数构造时间轴，不检查 `comm_count` 缺口。丢包两侧数据会被拼入同一滑窗，事件时间整体提前，可能产生虚假特征峰值或漏检真实事件。
- **严重性**：中

## Tab3 (eDAS) 问题分析

**问题 T3-01：`_storage_timer` 回调在主线程执行，可能周期性阻塞 UI**

- **位置**：`src/das_tab3/das_tab3_manager.py:36–39`

```python
self._storage_timer = QTimer()
self._storage_timer.setInterval(1000)
self._storage_timer.timeout.connect(self._maybe_store_snapshot)
```

- **分析**：`QTimer` 的回调在主线程 Qt 事件循环驱动，若 `_maybe_store_snapshot` 包含磁盘写入或大块 numpy 数据处理（如 `np.savez_compressed`），每秒执行一次会导致 UI 短暂冻结（10–200 ms），用户感知为界面卡顿。
- **严重性**：**高**（直接在主线程执行磁盘写入）

---

**问题 T3-02：联合存储文件大量重叠，写放大严重**

- **分析**：`_storage_timer` 固定每 1 秒触发，`interval_seconds` 只决定回看窗口大小，不是分块时长。若 `interval_seconds = 10 s`，相邻文件之间约 90% 的数据重复，造成严重写放大和 CPU 浪费。应改为保存 `[last_saved, current)` 的不重叠增量 chunk。
- **严重性**：中

---

**问题 T3-03：FIP 与 DAS 对齐仅检查 online 状态，不验证真实时序**

- **分析**：两路均 online 即返回 `aligned` 状态，未验证 `comm_count` 相等、时间差、包时长或时钟同步质量。FIP 是会话内归一化计数，DAS 是原始计数，两者不在同一计数域，直接做 `comm_count × 0.2s` 对齐存在系统误差。长时间运行后 TCP 传输抖动带来的到达时刻偏差会累积，影响联合分析精度。
- **严重性**：中（对联合定位准确性有影响）

## 优化方案（含实施顺序）

### 设计原则

在开始优化前，需明确以下四条约束，它们贯穿所有改动：

1. **降采样保持抽点方式**：所有降采样均保持 `data[::factor]` 的直接抽点形式，不引入任何抗混叠低通滤波器。
2. **完整数据通路不丢包**：存储链路和检测链路（Tab2）所获取的数据必须连续完整，不能因数据量大或处理速度不足而丢弃任何数据包。
3. **显示波形连续无遗漏**：Tab1 时域波形必须实时连续展示，采集期间发生的所有声音信号均应在波形中可见，不允许因队列满等原因跳帧或停止更新。
4. **完整数据通路与显示通路解耦**：存储/检测链路不依赖、不受制于显示链路的队列状态，两条链路相互独立运行。

这四条约束的核心架构含义是：**主线程绝对不阻塞**（消除 T1-08），**完整链路通过独立队列和独立线程接收原始包**（消除 T2-01 的根因），**显示链路使用足够大的缓冲**以保证连续性（消除 T1-05）。

目标架构如下：

```
RawDataPacket（主线程，put_nowait）
├── DataProcessingThread（绘图 + PSD + Tab2/Tab3）
│       Queue maxsize=200（put_nowait，队列满时覆盖最旧）
│       ├── TimedomainPlotThread（Queue maxsize=100）
│       ├── PSDPlotThread（Queue maxsize=20）
│       ├── Tab2 检测链路（独立接收，见下）
│       └── Tab3 DAS 对齐链路
│
└── DataStorageThread（独立原始包存储）
        Queue maxsize=2000（put_nowait，队列满时记录丢弃并告警）
        永不阻塞主线程

Tab2 独立原始包链路（put_nowait）：
RawDataPacket → Tab2RawDispatchThread → FIPFeatureWorker
```

### 第一阶段：消除主线程阻塞（P0 级，最高优先级）

**目标**：消除所有可能导致主线程阻塞的路径，保证 UI 始终可响应。

#### 1.1 修复存储入队阻塞（解决 T1-08）

将 `DataStorageThread.add_raw_packet()` 的入队方式从 `block=True` 改为 `put_nowait`，并在队列满时记录告警而非阻塞：

```python
# src/fip_tab1/fip_tab1_manager.py
from queue import Full

def add_raw_packet(self, packet: RawDataPacket):
    if not self.enabled:
        return
    try:
        self.input_queue.put_nowait(packet)
        self.stats['raw_packets_enqueued'] += 1
        self.stats['raw_queue_peak'] = max(
            self.stats['raw_queue_peak'], self.input_queue.qsize())
    except Full:
        self.stats['storage_failure_count'] += 1
        self.logger.error(
            'Storage queue full, dropping packet #%d', packet.comm_count)
```

同理，`DataProcessingThread.add_raw_packet()` 若有类似阻塞入队，一并改为 `put_nowait`。

**注意**：队列满时丢包虽然不理想，但这只在磁盘严重过载时发生，此时继续阻塞主线程会导致更严重的全面卡死。应配合第三阶段的磁盘监控给出明确告警。

#### 1.2 修复停止时未排空存储队列（解决 T1-09）

在 `OptimizedTab1ThreadManager.stop()` 中实现两阶段停止：先停止上游分发（不再向存储队列入队），等待存储线程排空后再真正停止：

```python
# 两阶段停止示意
def stop(self):
    # 阶段一：停止上游，标记"正在排空"
    self._dispatching = False          # 新包不再分发给存储线程
    self.storage_thread.begin_drain()  # 存储线程继续处理直到队列空

    # 阶段二：等待排空确认（带超时）
    drained = self.storage_thread.wait_drain(timeout_ms=10000)
    if not drained:
        self.logger.warning('Storage drain timeout, %d packets may be lost',
                            self.storage_thread.input_queue.qsize())

    # 阶段三：真正停止
    self.storage_thread.stop()
    self.storage_thread.wait(3000)
```

存储线程需配合增加 `begin_drain()` 状态：收到排空指令后继续处理队列中的包，直到队列为空再退出。

#### 1.3 将日志级别从 DEBUG 改为 INFO，并限制每包日志频率（解决 T1-01）

```python
# src/main.py:112
logging.basicConfig(level=logging.INFO, ...)

# src/main.py:348 - 每包打印改为每 50 包一次
if packet.comm_count % 50 == 0:
    self.logger.info("MAIN: packet #%d, size=%d",
                     packet.comm_count, len(packet.phase_data))
```

同时为关键后台线程（DataStorageThread、DataProcessingThread）的循环内日志添加相同节流逻辑。

#### 1.4 修复 Tab3 存储在主线程执行（解决 T3-01）

`DASTab3Manager._maybe_store_snapshot` 当前由主线程 `QTimer` 直接调用并执行 `np.savez_compressed`。应将存储操作移入独立 `QThread` 或 `threading.Thread`：

```
主线程 QTimer (1 s) → 将当前数据切片（不可变引用）放入存储请求队列
                         ↓
                   DASStorageThread（独立线程）
                         ↓
                   np.savez_compressed 写盘
```

主线程仅做浅拷贝或 numpy 数组视图的引用传递（O(1) 操作），不执行任何 I/O。

### 第二阶段：保证显示波形连续（P1 级）

**目标**：保证时域波形实时连续，不因队列满而丢帧，采集期间任何声音信号均在波形中可见。

#### 2.1 增大时域绘图队列（解决 T1-05）

将时域绘图线程的输入队列从 `maxsize=10` 扩大到 `maxsize=200`，为 UI 主线程短暂忙碌期间提供足够缓冲：

```python
# src/fip_tab1/fip_tab1_manager.py:207
self.input_queue = Queue(maxsize=200)  # 从 10 → 200
```

maxsize=200 对应约 40 秒的包缓冲（5 Hz × 200 = 1000 s，实际 200 包 = 40 s 显示数据），内存消耗约 200 × 40000 × 8 字节 = 64 MB，可接受。

#### 2.2 时域缓冲区改用固定容量双端队列（解决 T1-06）

用 `collections.deque(maxlen=N)` 代替 `list`，消除 O(N) 的滑窗裁剪遍历：

```python
from collections import deque

MAX_DISPLAY = int(window_duration * display_sample_rate * 1.5)
self.data_buffer = deque(maxlen=MAX_DISPLAY)
self.time_buffer = deque(maxlen=MAX_DISPLAY)
# 绘图时直接转换：np.array(self.data_buffer)，O(N) 但仅在绘制时执行一次
# 不再需要 keep_indices 遍历
```

`deque(maxlen=N)` 的 `append` 为 O(1)，超出 maxlen 时自动从左侧丢弃最旧数据，完全不需要手动裁剪循环。

#### 2.3 增大 PSD 队列（解决 T1-07）

```python
# src/fip_tab1/fip_tab1_manager.py:386
self.input_queue = Queue(maxsize=20)  # 从 5 → 20
```

#### 2.4 为 Tab2 建立独立原始包接收路径（解决 T2-01）

当前 Tab2 通过 `data_processor.data_processed` 信号接收数据，与绘图链路共用同一队列，绘图丢包等于检测丢包。应仿照 Tab1 存储线程的模式，为 Tab2 建立独立的原始包接收路径：

```
# 新增路径（仿照 DataStorageThread 的双路分发）
RawDataPacket → Tab2RawInputQueue (put_nowait, maxsize=500)
                      ↓
              Tab2RawProcessingThread
                      ↓（独立展开 + 抽点降采样）
              FIPFeatureWorker（当前）
```

具体实现步骤：
1. 在 `OptimizedTab1ThreadManager.process_raw_packet()` 中，将 `RawDataPacket` 同时分发给 Tab2 的原始包队列（`put_nowait`）。
2. Tab2 内部新增一个 `Tab2RawProcessingThread`，独立完成相位展开 + `[::5]` 抽点降采样，生成与当前 `ProcessedData.downsampled_data` 等效的数据后，交给 `FIPFeatureWorker`。
3. 断开 `data_processor.data_processed.connect(tab2_manager.process_processed_data)` 的连接。

这样 Tab2 的检测数据完全独立于绘图链路，不受绘图丢帧影响。

### 第三阶段：增强健壮性与可追溯性（P2 级）

**目标**：修复协议层漏洞、改善可观测性、提高停止/重启可靠性。

#### 3.1 修复协议失步问题（解决 T1-03）

在 `fip_tcp_server.py` 的包头解析逻辑中，遇到非法 `data_length` 时立即关闭当前连接（而非 `continue`），触发重连，而非试图在失步的字节流中继续解析：

```python
if data_length <= 0 or data_length > MAX_EXPECTED_LENGTH:
    self.logger.error('Invalid data_length=%d, closing connection for resync', data_length)
    self.client_socket.close()
    break  # 退出接收循环，由外层重新等待连接
```

中期目标：在协议头中增加固定 magic word（如 `0xFEEDCAFE`），在包头校验前先验证 magic，失配时快速搜索下一个 magic 位置，无需断连即可重同步。

#### 3.2 修复 `_recv_exact` 无法快速响应 stop（解决 T1-02）

```python
except socket.timeout:
    if not self._running:
        return None  # 立即退出，不再等待下一次超时
    continue
```

#### 3.3 修复 Tab3 联合存储文件重叠（解决 T3-02）

将 `_maybe_store_snapshot` 的逻辑改为：每次只保存自上次存储结束点起的新增数据（增量 chunk），而非每次都取最近 N 秒的全量快照：

```python
# 伪代码
def _request_incremental_store(self):
    new_data = self.coordinator.get_since(self._last_snapshot_end_comm)
    if new_data:
        self._das_storage_thread.enqueue(new_data)
        self._last_snapshot_end_comm = new_data.end_comm
```

#### 3.4 缺包时重置相位展开状态（解决 T1-15）

在 `DataProcessingThread` 的包处理逻辑中，检测到 `comm_count` 不连续（`curr - prev != 1`）时，调用 `self.phase_unwrapper.reset()` 重置状态，并在输出中插入 gap marker，告知下游（Tab2、存储）此处存在数据缺口：

```python
if self._last_comm_count is not None and packet.comm_count != self._last_comm_count + 1:
    self.logger.warning('comm_count gap: %d → %d', self._last_comm_count, packet.comm_count)
    self.phase_unwrapper.reset()
    # 可选：向 ProcessedData 中添加 has_gap=True 字段
```
