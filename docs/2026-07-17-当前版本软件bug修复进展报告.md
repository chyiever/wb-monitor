## 1. 摘要

本报告用于说明 2026-06-10 Bug 分析总结中列出问题在当前本地版本中的修复进展，并给出后续开发优先级。

当前版本已经完成大部分会导致主线程阻塞、界面卡顿、停止丢尾包和 Tab3 主线程写盘的问题修复。尤其是 Tab1 存储入队阻塞、停止排空、日志节流、时域和 PSD 队列扩容、Tab3 DAS 后台存储和增量存储已经有明确代码实现。

## 5. 已完成修复说明

### 5.1 主线程阻塞和 UI 卡死风险

Tab1 存储入队已从阻塞式 `put(block=True)` 改为非阻塞入队。该改动直接消除了磁盘慢或队列满时主线程无限阻塞的风险。队列满时会记录 `storage_failure_count`，这是正确的降级行为，但也意味着磁盘长期过载时系统会选择保 UI 响应而不是无限保证存储完整。

Tab1 停止流程已经增加两阶段排空。停止时先让存储线程进入 drain 模式，再等待队列清空，最后停止所有线程。该方案能显著降低正常停止时尾部数据丢失概率。

### 5.2 绘图和 PSD 连续性

时域绘图队列已扩容至 200，PSD 队列已扩容至 20。时域缓冲改用 `deque(maxlen=...)` 后，长时间窗口下的滑动裁剪开销已经从显式遍历裁剪转为固定容量自动淘汰，改善了大窗口下的响应稳定性。

### 5.3 Tab2 停止和缺口处理

Tab2 触发存储线程新增 drain 流程，停止时先 flush 活跃事件并等待存储请求排空。特征计算线程新增 `comm_count` 缺口检测，缺包时重置信号缓冲和滤波器状态，避免跨缺口拼接产生虚假窗口。

### 5.4 Tab3 DAS 通信、绘图和存储

Tab3 当前本地改动进一步优化了 DAS 链路：

- 服务端按 `data_bytes` 和 `channel_count` 恢复矩阵，避免依赖浮点时长反推样本数。
- DAS TCP 接收端新增 `missing_packets` 统计，按 `comm_count` 检测缺口。
- Space-Time 图改为最近窗口多包滚动拼接，而不是只显示最新单包。
- DAS Channel 曲线增加最大点数控制，避免超长曲线拖慢 pyqtgraph。
- UI 增加 Missing 计数显示，并优化曲线 fast path 和颜色条范围刷新。
- 联合存储已迁移到 `DASStorageWorker` 后台线程，并以增量方式写入。

## 6. 未闭环问题与风险评估

### 6.1 P0：Tab2 独立原始包链路未实现

当前 Tab2 仍从 `DataProcessingThread.data_processed` 获取数据。该处理线程定位是绘图优先，队列满时允许丢旧包。因此 Tab2 检测链路仍可能受绘图处理链路丢包影响。

建议新增独立链路：

```text
RawDataPacket -> Tab2RawProcessingThread -> FIPFeatureWorker
```

该链路应独立完成相位展开、固定抽点降采样和缺口标记，不再依赖绘图处理结果。

### 6.2 P0：存储链路缺包后相位展开 reset 不完整

`DataProcessingThread` 已在缺包时 reset `PhaseUnwrapper`，但 `DataStorageThread` 是独立原始包存储链路，当前在 `_build_storage_request()` 中先执行相位展开，再在 `_append_request()` 中检测缺包。因此存储链路跨缺口仍可能被错误连续化。

建议在存储线程中维护上一包 `comm_count`，并在调用 `unwrap_phase()` 之前判断缺口并 reset。

### 6.3 P1：存储文件元数据语义不足

当前 `.npz` 存储仍存在三个问题：

- `timestamp` 字段仍是会话相对秒偏移，容易被误用为绝对时间。
- chunk 边界只记录包级 `start_comm_count` 和 `end_comm_count`，不能表达包内切分边界。
- `raw_comm_count` 未传递到存储层，发送端复位和断连场景不便追溯。

建议升级存储元数据 schema：

| 字段 | 建议处理 |
|---|---|
| `timestamp` | 改名为 `session_offset_seconds` |
| `stream_start_time` | 保留真实绝对时间，并明确含义 |
| `raw_comm_count` | 从 TCP 层传递到 `RawDataPacket` 和存储文件 |
| `start/end_comm_count` | 明确闭区间、半开区间或补充样本级 offset |

### 6.4 P1：相位单位判断依赖数值阈值

当前代码仍以 `np.max(np.abs(phase_data)) > 5` 判断是否需要除以 `pi`。该逻辑缺少显式数据来源语义，维护时容易误用于已经展开的数据。

建议为协议或数据对象增加明确字段，例如 `phase_unit=normalized_pi` 或 `phase_unit=rad`，避免基于数值范围猜测单位。

### 6.5 P2：PhaseUnwrapper 缺少锁保护

`PhaseUnwrapper` 仍直接读写 `_last_phase`。虽然当前竞争窗口较小，但在主线程 reset 和后台线程 unwrap 并发时仍存在理论风险。

建议使用 `threading.RLock` 包裹 `unwrap_phase()`、`reset()` 和 `get_status()` 中对内部状态的访问。

### 6.6 P2：Tab3 存储停止未显式排空

Tab3 已将写盘移入后台线程，但 `DASStorageWorker.stop()` 只是设置 `running=False` 并等待线程退出，没有像 Tab1 和 Tab2 那样提供显式 drain 语义。若停止时队列中仍有请求，仍可能存在尾部联合存储请求未写完的风险。

该问题不属于 2026-06-10 文档中的 T3-01 或 T3-02 主项，但建议后续补齐，以保持三个数据链路的停止语义一致。

## 9. 结论

当前版本已经完成大部分稳定性优化，尤其是主线程阻塞、日志 I/O、绘图缓冲、Tab3 主线程写盘和联合存储写放大等高影响问题已经明显改善。

但当前版本仍不满足“完全优化 2026-06-10 Bug 总结中所有问题”的标准。开发上应优先处理 Tab2 独立原始包链路、存储链路缺包 reset、存储元数据可追溯和相位单位语义这四类问题。完成这些后，系统的数据完整性、检测可靠性和离线分析可追溯性才算基本闭环。
