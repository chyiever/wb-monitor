# 2026-09-23 整体数据流稳定性评估与优化记录

## 1. 评估范围

本次按“数据从 TCP 接收到显示/存储落盘”的完整链路检查，重点覆盖：

- FIP Tab1 实时波形显示链路。
- FIP 独立存储链路。
- eDAS 独立存储链路。
- FIP/eDAS joint 联合存储链路。
- `comm_count` 时间对齐与缓存裁剪。

目标是：

```text
存储链路：不主动丢已接收数据，分文件后 comm_count 连续
显示链路：尽量流畅、低延迟，允许显示帧跳过但不影响存储
对齐链路：只写完整连续配对帧，未写盘帧不被缓存裁剪提前移除
```

## 2. 关键结论

### 2.1 存储链路

当前存储链路已经从“保护 UI 优先、队列满时丢包”调整为“连续性优先、队列满时背压”：

- FIP 独立存储：`DataStorageThread` 直接接收 `RawDataPacket`，不依赖 Tab1 显示处理结果。
- eDAS 独立存储：`EDASRawStorageWorker` 写 `.bin + .json`，队列满或预算压力时等待后台写盘线程消化。
- joint 联合存储：`DASStorageWorker` 游标只在写盘成功后推进，失败不会跳过帧。
- 对齐缓存：`AlignedSessionCoordinator.protect_unflushed_frames_after()` 保护 `_last_snapshot_end_comm` 之后尚未写盘的帧。

### 2.2 Tab1 实时显示链路

Tab1 显示链路仍采用“实时性优先”：

- `DataProcessingThread` 是显示/分析处理链路，队列满时丢旧保新，不影响 FIP 原始存储。
- `TimedomainPlotThread` 和 `PSDPlotThread` 本次改为队列满时丢弃最旧显示帧并接收最新帧，避免画面长期滞后。
- 时域波形和 PSD 刷新不再固定每 5 包一次，而是按 `packet_duration_seconds` 动态计算：
  - 0.2 s/包时约每 1 s 刷新一次；
  - 1.0 s/包时每包刷新一次。

因此，现场如果 FIP 单包时长设置为 `1 s`，Tab1 波形不会再因为固定 5 包节流而 5 秒才刷新一次。

### 2.3 时间对齐链路

时间对齐仍以 `comm_count` 为主键：

- FIP 和 eDAS 都推入 `AlignedSessionCoordinator`。
- joint 写盘前只取 `_last_snapshot_end_comm` 之后的新增帧。
- 新增帧只保留连续完整配对前缀；尾部单路先到的帧等待另一侧补齐。
- 如果某一路真实缺包，joint 不会静默生成 FIP/eDAS 时长不一致的文件；应先处理通信缺包或降低数据率。

## 3. 本次优化

### 3.1 Tab1 波形刷新动态节流

更新文件：`src/fip/manager.py`

旧逻辑：

```text
TimedomainPlotThread.update_interval = 5
PSDPlotThread.update_interval = 5
```

问题：

- 若 FIP 单包时长为 `1 s`，Tab1 时域波形和 PSD 实际约 `5 s` 才刷新一次。
- 画面会被误判为卡顿或不实时。

新逻辑：

```text
packets_per_update = round(1.0 / packet_duration_seconds)
```

效果：

- 单包 `0.2 s`：约每 5 包刷新一次，刷新周期约 `1 s`。
- 单包 `1.0 s`：每包刷新一次。
- 单包时长改变时，刷新节奏自动跟随，不需要手工改代码。

### 3.2 Tab1 显示队列丢旧保新

更新文件：`src/fip/manager.py`

旧逻辑：

- `TimedomainPlotThread` 队列满时丢弃新包。
- `PSDPlotThread` 队列满时静默忽略新包。

风险：

- UI 线程短时繁忙后，绘图线程可能持续处理旧显示帧，画面落后于实时数据。

新逻辑：

- 队列满时先丢弃最旧显示帧，再放入最新帧。
- 增加显示队列统计：`packets_enqueued`、`packets_dropped`、`queue_peak`、`plot_updates`。

说明：

- 这是显示链路策略，不代表存储丢包。
- 存储链路使用原始数据路径，不依赖 `TimedomainPlotThread` 或 `PSDPlotThread`。

### 3.3 FIP 独立存储改为无压缩 `.npz`

更新文件：`src/fip/manager.py`

旧逻辑：

```python
np.savez_compressed(file_path, **payload)
```

新逻辑：

```python
np.savez(file_path, **payload)
```

原因：

- `.npz` 仍是标准 Zip 容器，读取方式不变。
- 不压缩可显著降低 CPU 压缩耗时，减少存储队列积压。
- 当前目标是“不丢数据”和“连续落盘”，优先级高于压缩体积。

### 3.4 Tab1 停止 drain 尾段保护

更新文件：`src/fip/manager.py`

旧风险：

- `OptimizedTab1ThreadManager.stop()` 看到存储输入队列为空后就继续 stop。
- 但此时 `DataStorageThread` 可能仍在 flush 最后一段文件。
- 如果主线程随后并发调用 `end_run_cycle()` 或等待时间不足，尾段文件存在丢失风险。

新逻辑：

- `begin_drain()` 后等待 `DataStorageThread` 自己退出 run loop。
- 最多等待 `180 s`。
- 只有超时才强制 stop，并记录 warning。
- `DataStorageThread.run()` 结束时设置 `running=False`，状态更准确。

## 4. 当前工程边界

### 4.1 “不能丢数据”的前提

软件可以保证“不主动丢弃已经进入存储链路的数据”，但不能突破硬件极限：

- 如果 TCP 发送端或网络已经真实缺包，软件只能记录缺口，不能补造数据。
- 如果磁盘长期低于输入数据率，软件会背压上游，最终可能表现为接收变慢或发送端阻塞。
- 高吞吐场景应优先使用 joint `bin` 和 eDAS 独立 `.bin + .json`，目标盘建议 SSD/NVMe。

### 4.2 “波形刷新流畅”的边界

实时显示链路为了保持界面响应，会跳过旧显示帧：

- 这能让画面更接近当前数据，而不是排队播放过期数据。
- 显示跳帧不会导致存储文件缺帧。
- 若显示仍卡顿，优先降低显示点数、提高绘图降采样、缩小 eDAS 通道范围或降低 PSD 频率。

## 5. 验证建议

现场联调时建议同时观察：

- FIP/eDAS `接收包` 和 `缺包/失败`。
- joint 文件内 `comm_counts` 是否连续。
- joint 文件内 `fip_present` / `das_present` 是否均为 `True`。
- 日志中是否出现 `lossless backpressure`。
- Tab1 线程统计中的 `time_plot_stats` / `psd_plot_stats` 是否持续大量 `packets_dropped`。

如果出现大量显示 drop 但存储文件连续，说明只是 UI 显示压力；如果出现存储背压，则应优先检查磁盘吞吐和数据率配置。
