## 新增同步检验实现

### 数据记录

1. FIP 每收到一个 TCP 包，在 `PCCPMonitorApp._process_data_packet()` 中调用：

```python
receive_time = float(getattr(packet, "receive_timestamp", time.time()))
self.main_window.record_fip_packet_receive(packet.comm_count, receive_time)
```

2. eDAS 每解析一个 TCP 包，在 `DASTab3Manager._handle_raw_packet()` 中调用：

```python
receive_time = float(getattr(raw_packet, "receive_timestamp", time.time()))
self.main_window.record_edas_packet_receive(parsed.header.comm_count, receive_time)
```

3. 两个模块的接收时间戳均取自 TCP 接收线程“完整包体接收完成”的时刻，再按 `comm_count` 分别缓存，缓存上限为 `2000` 个序号，避免长时间运行占用过多内存。

### 显示指标

Data tab 中实时显示以下字段：

1. `首包时间差（FIP-eDAS）`：首个匹配 `comm_count` 的 `FIP接收时间 - eDAS接收时间`。该值一旦形成，不再受后续滑动缓存裁剪影响。
2. `最新同序号时间差（FIP-eDAS）`：最新匹配 `comm_count` 的 `FIP接收时间 - eDAS接收时间`。
3. `平均时间差（FIP-eDAS）`：当前所有匹配包的平均接收时间差。
4. `匹配包数`：已同时收到 FIP 和 eDAS 的相同 `comm_count` 数量。

### 判读方法

1. 若两套设备物理同步采集、每包长度均为 `1 s`，且同时启动通信，则同序号包的时间差理论上应接近 `0 s`。
2. 如果首包时间差稳定偏大，通常表示两个模块并未真正同时启动、某一侧先开始发送或接收端连接建立较晚。
3. 如果最新包时间差随运行时间持续漂移，可能表示两侧包周期或计数基准不一致。
4. 如果平均时间差稳定但有少量尖峰，优先检查主机调度、网络抖动和 GUI 主线程压力。
5. 当前实现使用主机接收时间，不是设备硬件时间戳；它适合联调阶段验证通信同步表现，不能替代设备内部时钟校准。

## 2026-07-19 同时启动通信异常定位与修复

### 本次日志范围

日志文件：`logs/pccp_monitor.log`

覆盖时间：`2026-07-18 23:48:41` 至 `2026-07-19 00:00:07`。

### 现象复盘

1. 单独点击 FIP 通信时，FIP TCP 服务端能够启动，客户端也能连接成功。日志中出现 `Client connected from ('127.0.0.1', ...)`，并且能解析到 `FIP_TCP_PARSE comm=0`、`FIP_TCP_PARSE comm=50` 等数据包。
2. 但 FIP 数据包在进入后续处理线程前被同步统计 UI 的异常打断。日志反复报错：

```text
Error processing data packet #0: 'MainWindow' object has no attribute 'data_sync_pair_count_label'
Error processing data packet #73: 'MainWindow' object has no attribute 'data_sync_average_delta_label'
```

3. 本次日志中，`data_sync_pair_count_label` 缺失错误出现 `107` 次，`data_sync_average_delta_label` 缺失错误出现 `11` 次。
4. 对应的 FIP 处理线程停止统计为 `packets_enqueued=0`、`packets_processed=0`，说明客户端连接和 TCP 解包已经发生，但数据没有进入 FIP 后续处理/显示/存储队列。
5. 同时启动时，eDAS 侧多次启动失败，日志中 `WinError 10049` 出现 `6` 次：

```text
Failed to start DAS server: [WinError 10049] 在其上下文中，该请求的地址无效。
```

6. 该错误表示程序尝试绑定的 eDAS 本地 IP 地址不属于当前主机可用地址。此时 eDAS 服务端无法监听，设备侧或客户端自然无法建立有效连接。

### 根因判断

1. GUI 重构后，Data tab 中实际创建的同步指标控件名称为 `data_sync_avg_delta_label` 和 `data_sync_match_count_label`。
2. 同步刷新逻辑仍引用旧名称 `data_sync_average_delta_label` 和 `data_sync_pair_count_label`。
3. FIP 包处理函数 `PCCPMonitorApp._process_data_packet()` 在主处理流程最前面调用 `record_fip_packet_receive()`。该调用抛出 `AttributeError` 后，被外层数据包处理异常捕获，导致当前包的后续入队、绘图、存储逻辑全部跳过。
4. eDAS 服务端启动时严格绑定配置 IP。若配置 IP 与当前网卡不匹配，`bind()` 直接失败，双模块同步启动时就表现为 eDAS 无法接收、FIP 侧也因为同步 UI 异常持续报错。

### 代码修复

1. 在 `MainWindow._create_data_sync_group()` 中为同步指标补充兼容别名：

```python
self.data_sync_average_delta_label = self.data_sync_avg_delta_label
self.data_sync_pair_count_label = self.data_sync_match_count_label
```

2. 在 `PCCPMonitorApp._process_data_packet()` 中，将 FIP 同步统计 UI 更新包裹为独立保护逻辑。即使同步显示刷新失败，也只记录 warning，不再中断 FIP 数据包的解析、入队、绘图和存储链路。
3. 在 `DASTab3Manager._handle_raw_packet()` 中，对 eDAS 同步统计 UI 更新做同样保护，避免 Data tab 显示问题反向影响 eDAS 数据处理。
4. 在 `DASTCPServer.start_server()` 中增加绑定回退策略：优先绑定用户配置 IP；若该 IP 触发 `OSError/WinError 10049`，自动回退绑定到 `0.0.0.0:port`，并输出 warning 日志保留证据。
5. eDAS 服务端启动失败时会显式关闭已创建的 socket，并将 `server_socket` 置空，避免失败后的半初始化状态影响下一次启动。

## 2026-07-20 长时间运行卡顿与通信时间差漂移修复

### 日志范围

日志文件：`logs/pccp_monitor_2026-07-19_10-06-32.log`

覆盖时间：`2026-07-19 10:06:32` 至 `2026-07-19 23:59:54`。

### 问题四：长时间运行后切换 View/Data/Setting 或曲线数据源仍卡顿

日志证据：

1. `Processing queue full` 共 `6424` 次，说明 FIP 后台处理链路在长时间运行后出现明显积压和丢弃旧包。
2. `TAB3_NODE das_tcp.slow_receive` 共 `10342` 次，eDAS 单包接收耗时大量超过 `1.5 s` 阈值，通信线程侧存在持续等待或调度延迟。
3. `TAB3_NODE plot_worker.slow` 共 `2593` 次，DAS 绘图载荷构造有较多慢帧。
4. `Input data outside expected range` 共 `10258` 次，FIP 相位范围告警高频写入日志，增加 FileHandler I/O 压力。

根因：

1. View 页曲线每次刷新都会调用 `_update_view_psd_curves()`，而 PSD 使用 Welch 计算，运行在 Qt 主线程。一次 payload 往往包含 FIP/eDAS 多条曲线更新，导致同一 UI 刷新周期可能重复触发 PSD 计算。
2. 用户切到 Data/Setting 或切换曲线源时，后台通信和绘图 payload 仍持续尝试更新 View 图件，`setData()`、`setImage()` 和 PSD 计算会抢占主线程事件循环。
3. FIP 相位输入范围告警虽然已节流，但日志显示输入长期远超 `[-1, 1]`，高频 warning 和错误语义仍会放大长时间运行压力。

修复措施：

1. `MainWindow.update_tab3_fip_curve()` 和 `MainWindow.update_tab3_plot_payload()` 在当前页不是 View 时直接跳过曲线和 Space-Time 图件刷新，只保留通信统计、存储、同步等后台链路继续运行。
2. `_render_tab3_curve()` 不再同步调用 PSD 更新，改为 `_request_view_psd_update()` 通过 `QTimer.singleShot(80, ...)` 合并短时间内的多次刷新，再受原有 `1 s` PSD 刷新间隔控制。
3. `reset_tab3_views()` 会清理挂起的 PSD 更新标记，避免清屏后旧调度补刷。
4. `validate_wrapped_phase_input()` 会修复非有限值和绝对值超过 `1e6` 的极端满量程异常点，并对修复日志按 50 包节流。
5. `PhaseUnwrapper.unwrap_phase()` 现在区分两类输入：`max_abs <= 1.1` 仍按归一化 `[-1, 1] -> [-pi, pi]` 处理；超过该范围的有限输入按工程/弧度相位直接展开，不再强行乘 `pi`。

影响范围：

1. 上述 UI 优化只减少隐藏 View 时的可见图件刷新，不影响 TCP 接收、FIP 原始处理、eDAS 原始接收、存储或 joint 对齐链路。
2. PSD 仍会在 View 可见且 PSD 开关打开时刷新，只是将同一短时间窗口内的重复刷新合并。
3. FIP 极端值修复只处理明显异常点；正常工程/弧度相位不做缩放。

### 问题五：通信时间差从约 `-0.1 s` 慢慢变为约 `-10 s`

根因：

1. 旧实现中 FIP 时间差记录发生在 `PCCPMonitorApp._process_data_packet()` 进入 Qt 主线程后，eDAS 时间差记录发生在 `DASTab3Manager._handle_raw_packet()` 解析后。两者都使用当时的 `time.time()`，不是 TCP 收完整包时刻。
2. 长时间运行后，日志显示 FIP 处理队列积压、eDAS 慢接收、DAS 绘图慢帧和主线程绘图压力同时存在。此时主线程和处理链延迟会被混入“通信时间差”，表现为差值越来越大。
3. 旧 `首包时间差` 由最近 `2000` 个缓存包重新计算：`common_counts[0]` 会随着缓存裁剪向后滑动，所以显示的“首包”其实会变成当前缓存窗口内的第一个匹配包，运行越久越不像真正首包。
4. 旧显示未标明方向，且曾按 `eDAS - FIP` 计算；现场读数为负时很难直接判断是谁先到。

修复措施：

1. FIP TCP server 在 `_recv_exact(data_length)` 完整收到包体后立即记录 `packet_receive_time`，写入 `DataPacket.receive_timestamp`。
2. eDAS TCP server 在 `_recv_exact(data_bytes)` 完整收到包体后立即记录 `packet_receive_time`，写入 `DASRawPacket.receive_timestamp`。
3. `PCCPMonitorApp._process_data_packet()` 和 `DASTab3Manager._handle_raw_packet()` 只转发 packet 自带的 `receive_timestamp`，不再用主线程/解析线程当前 `time.time()` 作为通信时间。
4. Data 页同步方向统一为 `FIP - eDAS`，标签显示为 `首包时间差（FIP-eDAS）(s)`、`最新同序号时间差（FIP-eDAS）(s)`、`平均时间差（FIP-eDAS）(s)`。
5. `MainWindow` 新增独立同步状态：`_sync_first_pair`、`_sync_latest_pair`、`_sync_delta_sum`、`_sync_delta_count` 和 `_sync_matched_counts`。首个匹配包一旦形成就固定保存，不再受 `2000` 包滑动缓存裁剪影响；最新和平均按新匹配包增量更新。
6. FIP TCP 统计补充 `missing_packets`、`packets_lost`、`loss_rate` 和 `last_comm_count`，Data 页通信统计可以用同一口径显示 FIP/eDAS 的接收包、缺包/失败、丢包率和最近 Comm。

判读调整：

1. 现在 `首包时间差（FIP-eDAS）` 为负，表示 FIP 完整包体到达主机的时间早于 eDAS；为正，表示 FIP 晚于 eDAS。
2. `首包时间差（FIP-eDAS）` 不应再随运行时间改变；若改变，优先检查是否发生了通信重启或同步统计被重置。
3. `最新同序号时间差（FIP-eDAS）` 和 `平均时间差（FIP-eDAS）` 仍会随新包进入而更新，它们用于观察运行中的抖动和漂移。
