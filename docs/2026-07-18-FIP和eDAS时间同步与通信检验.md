## 新增同步检验实现

### 数据记录

1. FIP 每收到一个 TCP 包，在 `PCCPMonitorApp._process_data_packet()` 中调用：

```python
self.main_window.record_fip_packet_receive(packet.comm_count, time.time())
```

2. eDAS 每解析一个 TCP 包，在 `DASTab3Manager._handle_raw_packet()` 中调用：

```python
self.main_window.record_edas_packet_receive(parsed.header.comm_count, time.time())
```

3. 两个模块的接收时间按 `comm_count` 分别缓存，缓存上限为 `2000` 个序号，避免长时间运行占用过多内存。

### 显示指标

Data tab 中实时显示以下字段：

1. `首次包时间差`：首个匹配 `comm_count` 的 `eDAS接收时间 - FIP接收时间`。
2. `最新同序号包时间差`：最新匹配 `comm_count` 的 `eDAS接收时间 - FIP接收时间`。
3. `平均时间差`：当前所有匹配包的平均接收时间差。
4. `已匹配包数`：已同时收到 FIP 和 eDAS 的相同 `comm_count` 数量。

### 判读方法

1. 若两套设备物理同步采集、每包长度均为 `1 s`，且同时启动通信，则同序号包的时间差理论上应接近 `0 s`。
2. 如果首次包时间差稳定偏大，通常表示两个模块并未真正同时启动、某一侧先开始发送或接收端连接建立较晚。
3. 如果最新包时间差随运行时间持续漂移，可能表示两侧包周期或计数基准不一致。
4. 如果平均时间差稳定但有少量尖峰，优先检查主机调度、网络抖动和 GUI 主线程压力。
5. 当前实现使用主机接收时间，不是设备硬件时间戳；它适合联调阶段验证通信同步表现，不能替代设备内部时钟校准。

## 2026-07-19 同时启动通信异常定位与修复

### 本次日志范围

日志文件：`logs/pccp_monitor.log`

覆盖时间：`2026-07-18 23:48:41` 至 `2026-07-19 00:00:07`。

### 现象复盘

1. 单独点击 FIP 通信时，FIP TCP 服务端能够启动，客户端也能连接成功。日志中出现 `Client connected from ('127.0.0.1', ...)`，并且能解析到 `FIP_TCP_PARSE comm=0`、`FIP_TCP_PARSE comm=50` 等数据包。
2. 但 FIP 数据包在进入后续处理线程前被同步统计 UI 的异常打断。日志反复报错：

```text
Error processing data packet #0: 'MainWindow' object has no attribute 'data_sync_pair_count_label'
Error processing data packet #73: 'MainWindow' object has no attribute 'data_sync_average_delta_label'
```

3. 本次日志中，`data_sync_pair_count_label` 缺失错误出现 `107` 次，`data_sync_average_delta_label` 缺失错误出现 `11` 次。
4. 对应的 FIP 处理线程停止统计为 `packets_enqueued=0`、`packets_processed=0`，说明客户端连接和 TCP 解包已经发生，但数据没有进入 FIP 后续处理/显示/存储队列。
5. 同时启动时，eDAS 侧多次启动失败，日志中 `WinError 10049` 出现 `6` 次：

```text
Failed to start DAS server: [WinError 10049] 在其上下文中，该请求的地址无效。
```

6. 该错误表示程序尝试绑定的 eDAS 本地 IP 地址不属于当前主机可用地址。此时 eDAS 服务端无法监听，设备侧或客户端自然无法建立有效连接。

### 根因判断

1. GUI 重构后，Data tab 中实际创建的同步指标控件名称为 `data_sync_avg_delta_label` 和 `data_sync_match_count_label`。
2. 同步刷新逻辑仍引用旧名称 `data_sync_average_delta_label` 和 `data_sync_pair_count_label`。
3. FIP 包处理函数 `PCCPMonitorApp._process_data_packet()` 在主处理流程最前面调用 `record_fip_packet_receive()`。该调用抛出 `AttributeError` 后，被外层数据包处理异常捕获，导致当前包的后续入队、绘图、存储逻辑全部跳过。
4. eDAS 服务端启动时严格绑定配置 IP。若配置 IP 与当前网卡不匹配，`bind()` 直接失败，双模块同步启动时就表现为 eDAS 无法接收、FIP 侧也因为同步 UI 异常持续报错。

### 代码修复

1. 在 `MainWindow._create_data_sync_group()` 中为同步指标补充兼容别名：

```python
self.data_sync_average_delta_label = self.data_sync_avg_delta_label
self.data_sync_pair_count_label = self.data_sync_match_count_label
```

2. 在 `PCCPMonitorApp._process_data_packet()` 中，将 FIP 同步统计 UI 更新包裹为独立保护逻辑。即使同步显示刷新失败，也只记录 warning，不再中断 FIP 数据包的解析、入队、绘图和存储链路。
3. 在 `DASTab3Manager._handle_raw_packet()` 中，对 eDAS 同步统计 UI 更新做同样保护，避免 Data tab 显示问题反向影响 eDAS 数据处理。
4. 在 `DASTCPServer.start_server()` 中增加绑定回退策略：优先绑定用户配置 IP；若该 IP 触发 `OSError/WinError 10049`，自动回退绑定到 `0.0.0.0:port`，并输出 warning 日志保留证据。
5. eDAS 服务端启动失败时会显式关闭已创建的 socket，并将 `server_socket` 置空，避免失败后的半初始化状态影响下一次启动。
