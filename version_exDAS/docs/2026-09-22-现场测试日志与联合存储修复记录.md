# 2026-09-22 现场测试日志与联合存储修复记录

## 背景

现场测试日志文件：`logs/新建文本文档.txt`。

测试日志暴露出三个主要问题：

1. 程序只生成原始 `.log`，没有自动汇总测试日志文档。
2. View 页 DAS Space-Time 图存在跳动/空白帧现象，不呈现连续滚动效果。
3. FIP/eDAS 联合存储选择 `h5` 时，测试环境缺少 `h5py`，日志连续出现 `No module named 'h5py'`，导致 joint 写盘全部失败，本地联合存储目录看不到文件。

现场还观察到 Data 页预估数据量约 `180 MB/s`。该数值本身是吞吐压力提示，但旧 UI 标签只写“预计文件”，没有明确区分“单文件/单 chunk 体量”和“实时写入速率”，容易误读。

## 日志根因

联合存储失败的直接日志：

```text
DAS storage _save failed: No module named 'h5py'
TAB3_NODE manager.joint_storage failed end_comm=... cursor stays=-1; frames will be re-collected
DASStorageWorker ... save_failures=111
```

原因是 joint 格式被设置为 `h5`，但 `requirements.txt` 当前没有强制安装 `h5py`。旧逻辑会让每次 joint 写盘都抛异常，cursor 不推进，下一轮继续重收集同一批帧，最终表现为联合存储一直失败、目录中没有 joint 文件。

## 修复内容

### 1. 自动测试报告

更新文件：`src/main.py`

- 新增 `TestReportWriter`。
- 程序退出清理时读取本次 `pccp_monitor_*.log`，自动生成：

```text
logs/test_reports/test_report_YYYY-MM-DD_HH-MM-SS.md
```

- 报告包含：
  - 原始日志路径
  - 日志时间范围
  - ERROR/WARNING 摘要
  - Traceback/ModuleNotFoundError 摘要
  - 存储相关日志
  - 性能与 slow 相关日志

这样现场测试结束后，不需要手工从 `.log` 中复制错误行，也能留下可读的测试日志文档。

### 2. Space-Time 连续滚动与空白帧

更新文件：`src/das/plot_worker.py`、`src/ui/main_window.py`

修复点：

- `DASPlotWorker._build_space_time_payload()` 中，滚动 buffer 溢出时只丢弃新数据块实际需要的列数。
- 旧逻辑还会额外按“单次平移(s)”丢弃整段窗口，导致瀑布图跳动，现场容易看到不是连续滑动，而是大段刷新。
- UI 端收到空矩阵/空 payload 时，不再调用 `_reset_tab3_space_time_image()` 把图清成 1x1 空白图，而是保留上一帧并写 debug 日志。

预期效果：

- DAS 包持续到达时，Space-Time 图按新数据块连续向前滚动。
- 不再出现“先显示一次 time-space 图、下一次变空白、之后又正常刷新波形”的交替视觉问题。

### 3. 联合存储缺依赖回退

更新文件：`src/das/joint_formats.py`、`src/ui/main_window.py`

修复点：

- `save_joint("h5", ...)` 捕获缺少 `h5py` 的 `ModuleNotFoundError`。
- 缺少 `h5py` 时自动回退到 `bin` 联合格式，并写 warning 日志。
- 联合存储默认格式从 `npz` 改为 `bin`。
- UI 成功计数补充识别 `.h5` 后缀。

原因：

- `bin` 是无压缩顺序二进制流写盘，不依赖 `h5py`，适合 `180 MB/s` 级别的现场数据吞吐。
- `npz`/`h5 gzip` 在高吞吐下可能受到压缩和依赖影响，更适合短时验证或离线兼容需求。

### 4. Data 页存储估算显示

更新文件：`src/ui/main_window.py`

旧显示：

```text
联合: ~360.0 MB
```

新显示：

```text
联合: ~360.0 MB (~180.0 MB/s)
```

说明：

- 前一个值表示当前 `联合间隔(s)` 下的单 chunk 估算体量。
- 括号内表示实时写入速率。
- eDAS 速率按包头 `packet_duration_seconds` 换算，不再把单包体量误读为每秒体量。

## 使用建议

1. 现场高吞吐联合存储优先使用 `bin`。
2. 如果必须使用 `h5`，需要在目标 Python 环境安装 `h5py`；未安装时当前版本会自动回退到 `bin`，避免测试数据完全无法落盘。
3. `180 MB/s` 已经是较高写盘压力，建议确认存储盘为 SSD/NVMe，并避免把 joint、eDAS-only、系统日志同时写到低速移动盘。
4. 若 Space-Time 仍出现明显卡顿，优先调大 `时间降采样` 或减小通道范围，保证 UI 绘图矩阵维持在 `space_time_max_pixels` 附近或以下。

## 追加修复：npz 联合文件中 FIP 2 秒但 DAS 只有 1 秒

### 现象

现场把联合存储格式改为 `npz` 后，虽然 Data 页联合存储间隔设置为 `2 s`，但生成的联合文件里：

- FIP 数据约 `2 s`
- DAS 数据只有约 `1 s`

### 根因

联合存储按 `comm_count` 从对齐缓存里取新增帧。旧逻辑取的是 FIP/eDAS 的 `comm_count` 并集：

```text
comm=0: FIP 已到，DAS 已到
comm=1: FIP 已到，DAS 还没到
```

当 FIP 第 2 个包先到、DAS 第 2 个包稍后才到时，旧逻辑已经认为 chunk 覆盖 `0~2 s`，并把两帧入队写盘。此时第 2 帧的 `das_packet=None`，所以 `.npz` 中会出现：

- `fip_present = [True, True]`
- `das_present = [True, False]`
- FIP 有两帧，DAS 只有第一帧

这不是 `.npz` 写入函数只写了一半，而是写盘触发太早，把尾部未到齐的 DAS 帧当成缺失帧写进了联合文件。

### 修复

更新文件：`src/das/manager.py`

`EDASManager._maybe_store_snapshot()` 在 joint 写盘前新增“完整连续帧”筛选：

1. 从 `_last_snapshot_end_comm` 之后取新增帧。
2. 只保留从开头开始、`fip_packet` 和 `das_packet` 都存在的连续前缀。
3. 如果尾部出现 FIP 先到但 DAS 未到齐，则暂不写入这部分尾帧，也不推进 cursor。
4. 下一轮 DAS 同序号包到达后，再把完整的 2 秒 chunk 写入 `.npz`。

修复后的行为：

```text
comm=0: FIP 已到，DAS 已到
comm=1: FIP 已到，DAS 未到
=> 不写 2 秒文件，继续等待

comm=1: DAS 到达
=> 写入 comm=0,1，FIP/DAS 均为 2 秒
```

### 注意

如果某个 `comm_count` 的 DAS 包真实丢失，而不是延迟到达，严格“完整连续帧”策略会等待该缺口，避免生成 FIP/DAS 时长不一致的联合文件。此时应先处理通信缺包或降低 eDAS 吞吐压力；否则 joint 文件会延后生成。

## 追加修复：分文件连续性与实时显示链路检查

### 用户关注点

1. 连续数据流即使被切分成多个文件，也必须保证落盘数据连续，不能因为分文件、队列满或写盘慢而主动丢帧。
2. 实时显示波形是否也存在同样的“分段不连续/丢数据”问题，需要明确区分显示问题和存储问题。

### 检查结论

存储链路：

- FIP 独立 `.npz`、eDAS 独立 `.bin + .json`、FIP/eDAS joint 三条存储链路均已改为连续性优先。
- 队列满或达到内存预算时，不再主动丢弃待写数据，而是记录 `lossless backpressure` warning 并等待后台写盘线程消化队列。
- joint 存储的 `_last_snapshot_end_comm` 只在写盘成功后推进；失败或过大请求不会让 cursor 跳过未保存帧。
- `AlignedSessionCoordinator` 新增未写盘帧保护线，joint 开启时不会因为普通缓存裁剪把 `_last_snapshot_end_comm` 之后的帧提前移除。
- joint 文件只写连续完整配对帧，尾部 FIP 或 eDAS 单路先到的帧会保留在缓存中等待另一侧补齐。

实时显示链路：

- DAS 实时显示使用 `DASPlotWorker` 的有界队列，队列满时允许丢弃旧绘图帧，只保留较新的画面。
- FIP 处理/显示链路也可能在高负载下跳过旧显示帧，以避免界面长期卡死。
- 这类显示跳帧不等价于存储丢帧；存储链路使用原始数据路径和独立写盘线程，不依赖绘图队列。
- Space-Time 图的滚动空白问题已单独修复：滚动缓存只裁剪实际溢出列，空 payload 不再清空当前图像。

### 工程取舍

当前版本明确采用：

```text
存储链路：连续性优先，必要时背压上游，不主动丢待写数据
显示链路：实时性优先，必要时跳过旧绘图帧，不影响存储文件
```

如果磁盘长期低于输入速率，软件不能凭空保存超出硬件能力的数据；它会通过背压、慢写盘日志和 UI 状态暴露问题。现场高吞吐数据（例如约 `180 MB/s`）应优先使用 `bin`，并确认目标盘为 SSD/NVMe。
